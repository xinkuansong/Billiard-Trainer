# UI 打磨基准（W0）

> 本文件是本轮「页面 / UI / 交互体验打磨」的唯一评审基准。所有审阅产出（findings）必须对照本基准，且服从「红线」与「出局规则」。
> 萃取来源：项目 19（`/Users/song/projects/19.apple_design`）的 apple-design（Apple WWDC 流体界面原则）、emil-design-eng（动效决策框架）、microinteractions（微交互四要素）、refactoring-ui（视觉层级原则）；结合本代码库既有设计系统实况。
> 生成日期：2026-07-13。

---

## 0. 红线（凌驾于一切标准之上）

1. **不改变功能语义**：任何 finding 不得建议增删功能、改变交互模型（如求解/自由双模式、chips 过滤、仪表柱、球库带的语义）、改变信息架构或页面结构。
2. **不削弱内容展示**：台面演示、解线、轨迹、数据是主角。任何「按标准整改」若会让展示效果变弱，一律不提。
3. **每条 finding 必须自证「语义影响：无」**，否则出局。

### 出局规则（以下议题本轮不收录）

- Dynamic Type / 固定字号迁移 —— `Typography.swift` 注释明确「克制 + 数据为主角」是既定设计取向，固定字号是有意为之，**不作为问题**。
- Reduced Motion 合规 —— 合规议题，另轮单独议。
- Liquid Glass / iOS 26 新设计语言 —— min target iOS 17，不适用。
- 无障碍（VoiceOver 等）系统性补齐 —— 另轮。
- 性能优化（除非动效卡顿直接可感知且有代码证据）。

## 1. 现有设计语言快照（评审时的「本地真源」）

### 1.1 Token（`QiuJi/Core/DesignSystem/`）

- **字体**：`Font.bt*` 全套（btDisplay 44 → btMicro 10），使用原则见 `Typography.swift` 头注释（根 Tab 页标题 `btLargeTitle`、卡片标题 `btHeadline`/`btTitleMedium`、展示级仅限单屏核心数据）。**页面直接写 `.system(size:)` 而不用 token，属 D 类 finding**（除台面内标注/Canvas 绘制文本——那是内容渲染，不是 UI chrome）。
- **间距**：`Spacing.xs(4)/sm(8)/md(12)/lg(16)/xl(20)/xxl(24)/xxxl(32)/xxxxl(48)`；圆角 `BTRadius.xs(6)…xl(20)/full(999)`。硬编码 magic 间距/圆角属 D 类 finding。
- **颜色**：`Color.bt*` 语义色（btPrimary/btAccent/btSuccess/btWarning/btDestructive、btBG 四级、btText 三级、btSeparator、台面专用 btTableFelt/btTableCushion/btBallCue/btPathCue 等）。硬编码 `Color(red:...)`/`.gray` 属 D 类 finding（台面/球体渲染除外）。
- **组件库**：`QiuJi/Core/Components/BT*.swift`（35+ 个：BTButton、BTChipRow、BTEmptyState、BTSceneFAB、BTShotInstrumentColumn、BTAimWheel、BTSpinPad、BTSegmentedTab、BTShimmer、BTPremiumLock…）。页面手写了组件库已有能力，属 D 类 finding。

### 1.2 动效现状（既成事实，作为基准值）

代码库实际收敛于两套 spring（普查数据 2026-07-13）：

| 用途 | 参数 | 现有使用 |
|---|---|---|
| 面板/卡片/常规状态切换 | `spring(response: 0.34, dampingFraction: 0.86)` | PositionPlay 系、SnookerTactics、ShotSimulation 等 9+ 处 |
| 模式切换/较大布局变化 | `spring(response: 0.35, dampingFraction: 0.75)` | BankShot/DiamondSystem/SceneAiming 6+ 处 |
| 零散 | `spring(duration: 0.3)`、`easeInOut(0.2)`、`opacity` 淡入 0.45s 等 | MainTabView 浮标、顶行过渡、试打进场 |

**基准判定**：与这两套值语义相同但参数漂移的（如 0.3/0.7），属 D 类收编对象；**演示/回放类动画（出杆、走位、进袋）是内容不是 UI chrome，时长不受 300ms 规则约束**。

## 2. 四类评审维度与检查要点

### A. 动效手感（motion feel）

依据：apple-design（流体界面）、emil-design-eng（动画决策框架）。

- **A1 响应性**：进场/出场动画应「先快后慢」（ease-out / spring）。`easeIn` 用于 UI 进出场 = P1。
- **A2 时长**：UI chrome 动画（按钮、面板、chips、sheet）≤300ms；tooltip/小元素 125–200ms；面板/抽屉 200–350ms。超时且无理由 = P2。演示/回放动画豁免。
- **A3 频率匹配**：高频操作（tab 切换、chips 点选、每杆都碰的按钮）动画应极短或没有；低频/首次（onboarding、成就、进场说明卡）可以有 delight。高频重动画 = P1。
- **A4 可打断性**：状态切换动画进行中再次触发，应从当前呈现值继续（spring 天然满足），不得跳变或锁死输入超过必要范围。回放/演示类的输入锁定属功能语义（不改），但**锁定期间的视觉反馈**（变暗、pill 提示）要到位。
- **A5 空间一致性**：元素从哪进就从哪出（enter/exit 同路径）；覆层/弹窗的 transform 起点应贴近触发源（sheet/modal 除外，居中即可）。
- **A6 突现突消**：元素出现/消失无过渡造成跳变 = P2；从 `scale(0)` 进场 = P2（应 `scale(0.95)+opacity`）。
- **A7 过弹**：无手势动量的 UI 用明显 bounce（dampingFraction < 0.75）= P3；bounce 只留给拖拽释放类。

### B. 微交互反馈

依据：microinteractions（触发-规则-反馈-循环）、apple-design §1（kill latency）。

- **B1 按压态**：可点元素应有按下即时反馈（scale 0.96–0.98 / 高亮 / opacity）。主要操作按钮无按压态 = P2。
- **B2 拖动跟随**：拖动中元素/数值 1:1 实时跟随（我们的球拖动、力度柱、瞄准轮已是此模式——检查有无例外）；只在松手后才更新 = P1。
- **B3 状态可见性**：求解中/演示中/加载中/保存中要有明确的进行时反馈；完成要有完成反馈；失败/无解要有诚实且友好的空态文案（对照 BTEmptyState 与「该袋暂无翻袋解」的既有水准拉齐）。缺进行时反馈 = P2。
- **B4 防误触与恢复**：破坏性操作（清空、删除、覆盖）有确认或可撤销；非破坏性操作不应弹确认（过度确认 = P3）。
- **B5 触觉/声音**：关键物理时刻（进袋、球碰撞、吸附对齐、完成一组）若已有 haptic/音效体系，检查覆盖是否一致；**不建议新增大面积 haptic**（保持克制）。
- **B6 循环细节**：多次出现的提示是否会疲劳（如每次都弹的说明卡是否有「记住已读」——试打说明卡已有此模式，检查其它覆层是否拉齐）。

### C. 视觉层级

依据：refactoring-ui、apple-design §12/§16。

- **C1 主配角对比**：台面/数据是主角，周边控件应退后（弱底色、小字号、低对比）；控件抢戏（高饱和大面积色块非主操作）= P2。
- **C2 权重匹配**：视觉权重应与重要性一致——主操作（击打/求解/开始训练）最显著，次操作（重置/上一杆）次之，危险操作用 btDestructive 且不放显眼首位。倒挂 = P2。
- **C3 间距节奏**：组内间距 < 组间间距（亲密性）；同类列表/卡片间距一致；贴边距统一用 Spacing token。目测拥挤或参差 = P2/P3。
- **C4 层级手段**：优先用 字重/字号/颜色深浅 建层级，而非加边框加底色；一屏内强调元素 ≤1 个焦点。
- **C5 Dark Mode 层级保真**：暗色下 surface 层级（btBG 四级）是否仍能区分卡片/背景/覆层；阴影在暗色下失效时是否有替代（描边/提亮）。
- **C6 文案与标签**：按钮/入口用具体动词（「上手试打」优于「更多」）；同一概念跨页面同一叫法。

### D. 一致性收编

依据：emil-design-eng（cohesion & tokens）、improve-animations（审计分类）。

- **D1 动效参数**：列出所审页面全部硬编码动画参数（spring/duration/easing），对照 §1.2 基准值标注：吻合 / 漂移（建议收编）/ 有理由的例外。
- **D2 同类交互同形态**：「重置」「下一解」「回放」「关闭」等动作在不同页面的位置、图标、形态是否一致；同类 pill/chips/FAB 的尺寸圆角是否一致。
- **D3 Token 逃逸**：硬编码颜色/字号/间距/圆角清单（依 §1.1 规则，内容渲染豁免）。
- **D4 组件复用**：页面内手写了 BT* 已有组件的替身。

## 3. Finding 输出格式（子智能体必须遵守）

每个审阅文件结构：

```markdown
# UI 打磨审阅：<范围名>（<文件清单>）

## 页面概述
<每页 2-3 句：这页给用户看什么、核心交互是什么——证明你读懂了再评>

## Findings

### F-<范围缩写>-01 <一句话标题>
- **类别**：A动效 / B微交互 / C视觉 / D一致性
- **位置**：`相对路径:行号`（必须真实，引用关键代码片段 1-3 行）
- **现状**：客观描述
- **问题**：对照基准第几条（如 A1、C2）
- **建议**：具体到参数/token 名/代码级改法
- **语义影响**：无（说明为什么不改变功能语义）
- **严重度**：P1 明显损害体验 / P2 可感知的粗糙 / P3 锦上添花

## D1 动效参数普查表
| 位置 | 当前值 | 判定（吻合/漂移/例外） |

## 存疑项（不确定是否越红线的，单独列出待主控裁决，不算 finding）
```

**纪律**：
- 只读代码，**禁止修改任何源码**；只写自己被分配的那一个 md 文件。
- 每条 finding 必须有真实 `文件:行号` 证据，禁止凭想象；不确定的放「存疑项」。
- 宁缺毋滥：P3 每范围最多 8 条，避免灌水。
- 严重度用「用户能否感知」判定，不用「违反标准的程度」判定。
