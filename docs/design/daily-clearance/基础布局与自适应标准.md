## 1. 适用范围与依据

- 当前设计覆盖手机横屏、iPad横屏及竖屏；手机竖屏仍属归档概念。先处理2D基础，功能展开保留已有契约，另轮设计。
- 主参考为用户当前16 Pro **Figma粗调**；历史16 Pro **原生参考图**用于解释操作关系。两者不是同一份布局，尺寸、字体和安全区不能混用。
- C23读取的五屏粗调与交接快照几何指纹一致；问题和原始数值见[分析数据](../../../output/daily-figma-workspace-20261006/analysis-c23.json)及[工作区C23](../../../tasks/daily-adaptive/FIGMA-WORKSPACE.md)。C21/C22为未认可候选，不能作为新标准。
- 用户明确的“球库贴桌沿”、共有控件位置与大小继承、双文件流程优先；工程便利和通用留白习惯不能覆盖这些要求。
- 后续分离角、走位等页面可以继承布局测量、组件尺寸、命名及验收方法；球库、开球、相机、计分等能力须逐页判定，不能直接复制每日功能集合。

## 2. 先统一测量对象

本分册的布局坐标均为**所属画板/页面左上角原点，x向右、y向下，单位逻辑pt**。不使用截图像素代替pt，不从此坐标推导SceneKit物理坐标。

|对象|定义与用途|不能混用的对象|
|---|---|---|
|窗口|App当前实际窗口及系统装饰边界|设备型号标称屏幕|
|页面安全区域|所属容器扣除实际系统遮挡后的交互区域，安全区只计一次|固定左右边距、Figma整张画板|
|舞台|场景承载和布局分配区域|实际显示出来的球桌面积|
|球桌外框T|2D真实可见桌体外轮廓的包围框，保留六袋；不计透明图像留边和伸出的球杆|图片Frame、台呢内框|
|台呢内框I|由真实球桌几何/投影得出的有效台面范围|桌外框；不能把外框强改为2:1|
|布局外框L|容纳组件、标签、读数的排版范围|内部圆盘或有效轨道|
|可见主体V|圆盘、按钮背景、球库胶囊、尺轨等实际可见形状|带透明留边的L|
|命中范围H|原生实际响应区域及手势路由|V、AX frame或Figma选中框|

每个关键组件登记L/V/H及其局部偏移。Figma只能直接确认L/V；未有原生证据时H标为“目标/待验证”。C23报告的球桌节点尺寸用于追踪修改，不能直接当作已核验的原生T。

2D球桌沿用真实资产比例，以统一倍率拟合可用区域；横竖屏旋转后保持同一几何。图像/场景边界有留边时先核实T再拟合，禁止通过压扁、裁袋或修改物理尺寸适配。

## 3. 关系约束：先定锚点，再求坐标

|编号|关系|规范与验收对象|
|---|---|---|
|BL01|球库与球桌|2D彩球胶囊可见下沿贴T上沿，设计间距0；不新增独立留白带，不覆盖库边/袋口。单行母球与彩球条同轴；双行时母球位于两行整体左侧，纵向居中。透明留边不算贴边。|
|BL02|彩球序列居中|单行目标球固定槽位序列中心=T中心；两行时每行分别对T中心；母球独立在左。母球+彩球整个父框不能作为居中对象。短玩法按自己的固定集合居中，进袋不删槽。|
|BL03|顶栏|返回标题、模式、更多的可见中心线协调；标题与球库冲突时调整各自可用区。球库保持BL01，不为了强行把所有内容挤在一行而离开球桌。|
|BL04|左右主轴|开球圆盘中心、方向轨道中心位于左操作轴；击球点圆盘、杆速轨道、击球按钮中心位于右操作轴。两轴距真实桌体左右外沿等距，以同宽60pt操作列包络控制净空：当前标准净空8pt、SE紧凑4pt，即轴距桌边38/34pt。同尺寸控件净空相等；较窄控件居中，不强求所有宽度的主体边缘齐平。扣除球桌图片留边和伸出杆尾后测量。|
|BL05|顶部成对入口|开球/击球点使用同档圆盘直径、同一中心高度；标签同字体、同基线。不得一侧量50外框、另一侧量48圆盘后宣称同尺寸。|
|BL06|双尺|左右有效轨道同宽、同长、同顶同底；标签基线一致。杆速读数另占空间，方向尺无需为此增加假刻度；不能强制两个总外框等高。|
|BL07|底部动作|正常左侧重打/回放纵向组合居左轴，右侧击球居右轴；各动作紧接所属尺下方，完整内容之间统一4pt。击球为60×60pt，位于杆速读数下4pt；不再强制左组合与右击球底边对齐，不用增加空隙拉齐底边。短屏左组可横排，整体以左操作区为锚，成员不再逐个强绑左轴。|
|BL08|垂直定位|左右操作组共用一套纵向锚。先在桌旁可用高度中完整放下两组，整组协调定位；不为填满iPad长边拆散入口、尺和动作，也不逐控件吸附窗口百分比。|
|BL09|空间冲突|检查真实V间净空、H间路由，以及H与球桌选球/瞄准范围的冲突。球库贴边是指定例外，不能推广为击球按钮贴桌、标签贴数值。|
|BL10|跨模式|同窗口、方向、尺寸档、基础状态下，共有HUD继承位置和尺寸。3D用稳定HUD参考锚，不跟着透视桌沿移动；相机为独有区域，取景单独验收。|

对齐目标为精确关系；Figma读数可允许不超过0.5pt的舍入差供核验，不能用容差掩盖错误锚点。原生像素对齐按实际屏幕倍率检查。描边/阴影另作视觉核对，不用阴影范围放大按钮命中区。

**球库计算示例：**设T为`(Tx, Ty, Tw, Th)`，目标序列宽`Cw`，其可见胶囊高`Ch`，则目标序列左边为`Tx + (Tw − Cw)/2`，胶囊上边为`Ty − Ch`。母球位置在此结果左侧独立推导。若父层内部有1pt留边，应换算局部偏移，不能直接令父层下沿=Ty后宣布可见胶囊已贴边。此示例只定义屏幕布局，不涉及物理坐标。

## 4. 组件尺寸和内部结构

### 4.1 三种尺寸档

以下是**下一轮精调拟采用的默认解**，不是系统标准或用户已认可画面。选择由可用容量决定，机型只作首轮样本；禁止按设备名称写死分支。宽屏手机通常保留常规档，平板横竖屏在容量允许时共用宽裕档。

|可见尺寸/字号，pt|紧凑档|常规档（16 Pro主参考）|宽裕档|依据及使用条件|
|---|---:|---:|---:|---|
|开球/击球点圆盘直径|48|48|56|48来自参考；56为平板拟定上限，不随桌高继续长大|
|重打/回放按钮主体|44×44|44×44|48×48|44来自参考；48需同步修正内部居中|

|目标球视觉直径|25|30|34|25/30有历史参考；34是宽裕档候选。槽位宽、分区间隔和H另算|

可见主体的宽裕档增长应在桌面已合理拟合、且操作确有收益后采用；不能先加宽侧列，再以“剩余宽度不足”缩桌。若宽裕档反而挤桌，保留常规档并记录取舍。

普通独立按钮以至少44×44的无歧义命中区为本项目设计目标，可见圆盘和图标不必等于H。球库27/32pt窄槽为历史待解决例外：不得为每个槽叠加互相覆盖的44宽H并宣称解决。完整AX名称、中心点可点击都不证明边界或手指体验。

### 4.2 间距与内部排版

|用途|本轮拟定基准|限制|
|---|---|---|
|球库—球桌|0|用户明确关系；见BL01|
|图标/圆盘—标签|2|紧凑的组件内部关系；不强行吸附4pt网格|
|同组独立动作间|4|检查H是否冲突；不够时重排，不能靠重叠命中区省空间|
|入口—尺、尺组—动作|4|与重打—回放一致，按完整组件外框测量；杆速标签、数值和底部内边距均计入|
|60pt侧列包络—实际桌外框|标准8，紧凑4|左右相等；窄控件居中后主体净空相应更大，原生命中保护另验|
|模式—更多|4起步|分别命中；文字和描边不相交|

4pt是组间调整单位，不约束所有文字度量、资产比例和描边。不得把所有空隙统一改成12/16来追求整齐，也不允许把0重叠作为充分验收。

- 圆形入口使用真正同尺寸V，图形与文字围绕V中心排版。容器放大时重设内部布局，不能保留左上角旧44内容。
- 尺宽、有效行程、端部内边距、标签、数字分别设值；两尺按有效轨道成对布局。常规参考外框44×174/44×190仅说明组成，不是永远固定的外框。
- 图标按同族占比及视觉重心调整；开球三角/三球保持相切和填充关系。字号、描边、圆角不跟随任意父层倍率变化。
- Figma文字临时替代字体须标注；原生字体度量和安全区回验后才能冻结。大字号通过自然高度、重排、局部滚动满足，不用整页缩小抵消字体需求。
- 球、袋、球杆及场景背景不能与HUD共用整体缩放系数；台面比例与游戏事实始终由资产/物理真源负责。

## 5. 按容量适配的确定顺序

### 5.1 常规拟合

1. 记录真实窗口、安全区、字号、模式、玩法和完整功能集合；测组件自然大小及目标H。Figma未知项明确标注，不能假填安全区=0。
2. 建立球库与T整体关系、左右成对操作区、顶栏区及3D独有区。2D/3D共有壳需要评估相机通道；不因为2D暂时没有相机按钮就自动删除预留，也不未经比较强制留一条宽空列。
3. 在完整可操作方案内拟合真实比例球桌，登记宽/高限制轴。球库贴桌关系参与拟合，不能事后塞入并盖袋口。
4. 对不足空间使用5.2的顺序；对剩余空间先判断能否增大桌面，再判断控件有界增长。最后调组件组的位置和光学对齐。
5. 对照用户粗调：若桌体缩小，给出具体占用、必要收益和被排除方案。没有容量理由，不沿用C21的627→612等收缩。

### 5.2 空间不足时

依次尝试，命中可行解即停止压缩：

1. 移除重复说明和无用途空白；维持统一4pt组间空隙，保留0pt球库贴边、正常文字及必要H。
2. 短高度把左侧重打/回放由竖排改横排，保留两项能力和禁用语义；不能因SE粗调没画回放而删除功能。
3. 调整顶栏占区/换行关系及操作组位置，主按钮维持60，比较对桌面、触达的实际收益；不缩小所有文字或整条仪表。
4. 仍放不下时，比较小幅缩桌与成对缩短轨道两种方案。144为优先有效行程，**120为首个拟定缩短候选**，不是已验证下限；轨道仍32宽、两端一致、文字独立。选择需要说明收益，并在代码阶段复核快慢滑、反向、边界、读数和声震。
5. 单行球库仍不足时，改为两行（用户2026-10-07确认）。保持球号顺序、固定槽位及球面尺寸，每行相对桌心居中，母球独立在左；最下一行可见下沿贴桌。完整量测两行高度与顶栏净空，优先利用桌上空白，不以滚动隐藏余球或继续缩球。两行仍不足时重新评估容量与可恢复呈现，不能强行越界。
6. 任一方案都不能完整操作时，进入明确的受限布局：保留返回、解释容量不足、提供恢复路径。具体呈现仍需设计验证，不用隐藏关键按钮或只输出`fits=false`交付。

近方形/小窗口可比较把部分操作放入桌上下空白的结构；原左右结构为对照。要同时比较实际T面积、触达、基础状态与展开态、3D近端遮挡，不能只凭桌宽增大通过。断点来自方案自然容量边界，并测边界两侧和恢复过程；不使用未经验证的型号或长宽比分支。

这些是设计样本，不是已确认的设备原生可用窗口；代码阶段按实际系统窗口/安全区另登记。真实iPad多窗口、近方形、极小窗口和大字号属于补充边界，不冒充正常设备效果图。

交接固定顺序：**2D基础精调 → 用户确认 → 同设备/方向共有项的位置与尺寸同步到3D粗调 → 用户调整3D → AI精调3D → 用户确认 → 继续下一组功能状态设计。全部约定设计完成后，由用户明确启动代码实施。** 功能展开单独成轮；基础认可不覆盖80张展开草稿。

同步白名单：返回、球库、模式外壳、更多、开球、击球点、方向、杆速、重打、回放、击球。按实际存在及语义匹配，不仅按文本近似匹配。同步几何和已定组件规格，保留3D选中态、场景/相机、独有控件及其状态。源缺功能先登记补齐，不据此删除目标功能。同步前保存源和目标快照，结束分别核对共有项差异与独有项未被误改。

## 7. 文件、组件与状态命名

- 每个功能两份文件：`球迹｜{功能}｜用户粗调`、`球迹｜{功能}｜精调待确认`；同文件包括该功能2D/3D、全部尺寸与相关展开状态。后续功能沿用结构，不把不同用途混入一个每日文件。
- 页面沿用`00｜说明与命名`、`01｜2D｜基础布局`、`02｜3D｜基础布局`、`03｜2D｜功能展开`、`04｜3D｜功能展开`、`05｜原生效果参考`、`90｜组件库`、`91｜输入快照`、`99｜原始图层备份`。
- 工作画板保持`{模式}／{设备及方向}／{状态}`，例如`2D／iPad 11 竖屏／默认`；尺寸放画板属性/说明，状态用说明标注草稿、待精调、待确认、已确认，避免每轮改工作画板名。归档副本加轮次/日期。
- 精调组件用`控件／方向尺`、`控件／杆速尺`、`控件／开球`等稳定功能名；内部用`背景`、`圆盘`、`有效轨道`、`刻度`、`标签`、`读数`。同功能可复用，模式状态和尺寸档另登记。禁止以Frame 123或复制后缀作为交付语义。
- 用户版继续独立高清图块、保比例，普通移动工具即可拖位置/四角缩放；精调版保留可编辑内部结构。两类编辑方式不同，不能声称图块内文字可直接编辑。
- 普通拖角验证必须覆盖尺、圆盘、按钮和横竖球桌；检查内容同步、比例、裁切，测试后精确恢复。只验K/Scale或W/H不算用户操作通过。
