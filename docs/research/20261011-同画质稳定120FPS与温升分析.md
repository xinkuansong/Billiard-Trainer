# 同画质稳定120FPS与持续温升分析

2026-10-11。目标已确认：保持画质、物理精度和交互效果不变，在支持的设备上争取稳定120FPS，持续使用时没有明显烫手感。本文承接[渲染计算分工与参数评估](20261011-渲染计算分工与参数评估.md)，以当前源码和已有实验判断可行性及投入顺序。

后续执行方式已按用户要求调整：直接制作候选版本，验证随实现推进，不以完整定位为前置。当前实施顺序以[同画质120FPS实施方案](20261011-同画质120FPS实施方案.md)为准；本文保留实验分析与风险依据。

**判断：这个方向值得继续，但目前不能承诺达成。我们曾在旧场景短时测得119.84FPS；持续帧率与温升仍未通过。当前R配置的无损阴影候选有短测收益，却未稳定保持到持续阶段。最值得投入的是当前完整页面的瓶颈定位，以及有证据支持的局部同效果优化。** 简单调低采样、抗锯齿或物理精度不符合本次目标；全面重写Metal也没有现成的收益证明。

## 目标的可检验含义

“稳定120”应指球运动、瞄准、拖球、镜头过渡等需要变化的画面，实际内容按120Hz呈现；静止画面保持最后一帧并按事件唤醒，可以保留相同效果与响应。强迫静止画面每秒重画120次，会增加无效工作。不能把运动降到60、重复旧帧、延迟球影更新计作完成120目标。

画质基线保留当前获认可的R球反射、台呢纤维及高光、球影和接触暗部、原生像素尺寸、4×MSAA、房间与桌球资产、曝光和色彩。物理基线保留同一求解模型、碰撞与入袋结果、实际运动时间及旋转；交互基线保留相机规律、触控响应、预测与回放语义。

120FPS的显示周期是8.33ms。设备必须有相应显示能力，用户选择120，且系统允许。Apple明确说明刷新率请求是提示，应用不能强制面板维持指定刷新率；低电量和热限制仍然有效。[Apple ProMotion说明](https://developer.apple.com/documentation/quartzcore/optimizing-iphone-and-ipad-apps-to-support-promotion-displays)

“不发烫”需要在固定设备、亮度、环境、外壳和未充电条件下验收持续温感，不能只看系统Nominal。现有报告已经出现过“系统仍Nominal，用户明显感觉发热”。因此可追求的是约定条件下长期流畅且温感可接受，不能把任意手机、任意环境下零温升作为软件保证。[真实使用反馈](../../output/render-system-audit-20261011/r1/REPORT.txt)

### 持续结果改变了候选的采用判断

r8仍为60FPS诊断，每720帧循环含480帧真实生产物理轨迹回放和240帧人工边界场景，按60FPS计算名义时长12秒；实际墙钟时长受帧节奏影响。候选先运行约120秒，结束Fair；随后原R约54.46秒触发Serious停止。双方共同完成的四个周期，每配置2880帧，得到：

| 场景 | 原R GPU命令均值 | 候选GPU命令均值 | 变化 |
| --- | --- | --- | --- |
| 整个共同窗口 | 14.300ms | 13.702ms | −4.18% |
| 真实轨迹段 | 11.213ms | 13.059ms | +16.47% |
| 人工边界段 | 20.476ms | 14.989ms | −26.80% |

候选真实段逐周期由9.791ms升到约15.2ms。可能涉及频率、GPU资源或队列行为，但目前没有硬件频率及计数器证明根因。两次运行之间约88秒，只确认体感和系统档位恢复，未确认内部温度相同；所以不能用“120秒对54秒”宣称温升改善，更不能把真实段变慢定性成算法必然退化。正确处置是保留候选、暂不投产。[r8完整结论](../../output/render-system-audit-20261011/r8/REPORT.txt)

## 时间预算与功耗预算应分别判断

**8.33ms是120Hz的呈现周期，不等于任意一个GPU命令buffer都必须小于8.33ms。** 我们自己的S331就是反例：实际119.84FPS，同时GPU命令跨度P95为10.68ms。流水线可以跨帧重叠，命令跨度也不等于GPU独占执行时间。因此不能把当前60FPS测试的9.76ms取倒数，得出“最高只能102FPS”；也不能由9.76ms到6ms计算出一个确定的必要优化百分比。

需要分别观察CPU更新与提交的关键路径、GPU真正执行和等待、帧间依赖、实际内容呈现时间。CPU与GPU可并行，二者不能简单相加；排队过多即使提高吞吐，也可能增加触控延迟。Apple的排查流程同样从持续运行进入GPU时间线，再查看具体pass、shader和资源依赖。[Apple性能分析方法](https://developer.apple.com/videos/play/meet-with-apple/242/)

历史120方案曾提出GPU P95≤6ms／P99≤7.5ms、CPU P95≤3ms作为初始内部预算；10月11日r4则将该轮60FPS独立诊断的6ms目标列为积极参考，而非必要门槛。两者适用范围不同，不能互相替换。判断本次120目标需要核对其对应预算以及实际呈现、持续温感和功耗；这些毫秒数是项目内部参考，不是Apple规定。[历史预算](../../tasks/render-quality-v62/UNIFIED-LIGHTING-120FPS.md) · [60FPS诊断口径](../../output/render-system-audit-20261011/r4/REPORT.txt)

功耗可用一个概念模型理解：活动期的逐帧动态功耗约为“每帧能量×每秒帧数”，整场平均还取决于活动时长比例、预测、CPU维护、屏幕及系统其他工作。**仅在每帧能量与其他条件不变的简化条件下，从60提高到120会把这部分逐帧功耗加倍；若还要保持这一部分功耗不变，每帧能量就需约减半。** 用户本次要求的是同画质与物理精度，现有数据没有测出可接受的能量上限，因此不能据此宣称项目一定需要优化50%，也不能把命令跨度下降10%当作省电10%。

这解释了为什么需要两条工作线：停绘、减少无效更新降低一场训练的平均消耗；减少活动期实际GPU与CPU工作，才有机会维持长时间120。前者不能掩盖后者不达标。

## 为什么不能继续只调几个参数

已有对照实际排除了几条看似简单的路线：

| 方案 | 已有结果 | 本次判断 |
| --- | --- | --- |
| 阴影精确归零后提前退出 | 球架／散台命令跨度分别约+1.15%／+2.62% | 没有性能收益证据 |
| 合并两遍支持域计算 | 约−1.30%／−0.14% | 收益小且未稳定，不足以成为120方案 |
| 循环外提球相对向量和距离平方 | 约+16.17%／+22.84%，所测图相同 | 算式减少不代表GPU更快；寄存器压力只是待证解释 |
| 4×MSAA改2× | 约省6%至7%，球缘与细线台阶更明显 | 不满足当前同画质要求 |
| RS阴影替换 | 球架更慢、散台更快；重叠影变浅并有亮点 | 性能与画质均未形成通用解 |
| 台呢PBR直接改constant或只输出emission | 曾明显变暗、纤维损失；分离输出仍有像素差 | 不能把PBR笼统视为可删除的重复工作 |

来源：[r4计算组织与MSAA](../../output/render-system-audit-20261011/r4/REPORT.txt)、[r3阴影对照](../../output/render-system-audit-20261011/r3/REPORT.txt)、[历史S345／S347](../../tasks/render-quality-v62/UNIFIED-LIGHTING-120FPS.md)。GPU编译后的寄存器、并发与带宽决定实际表现，需要计数器和时间线支持归因。[Apple shader优化示例](https://developer.apple.com/videos/play/wwdc2021/10148/)

台呢当前近影区每灯8×4、远区每灯2×2采样。每个采样同时参与方向／距离、BRDF与过滤阴影计算；shadowPossible既决定球影候选，又决定光照采样档位，样本数还改变阴影滤波半径。缩小高采样区域、先对每球求平均遮挡再相乘、延后更新阴影，都可能改变原有输出。这些不能包装成只省去无效求交。[台呢shader](../../QiuJi/Core/Scene/MobileReferenceLighting.swift)

## 我建议的投入顺序

### 先建立当前120下的完整成本证据

下一次最有价值的测量应以当前正常使用的R配置为主，锁定安装包、源码与资产身份，区分四段：出杆前方向／力度预测，球运动，自动镜头过渡，球停与镜头收敛后的空闲。用户已报告不手动旋转、连续击球数杆也会明显热，因此正常击球加自动镜头应成为首要场景；不能只测相机旋转或固定球架。

在同一确定性输入下，分别记录实际呈现身份、CPU关键路径、GPU执行／等待及主要pass。先用少量代表帧查硬件限制属于片元算术、纹理／带宽、几何、资源同步还是提交；再观察同一物理帧在初段和变慢阶段的差异。重型抓帧与低扰动功耗录制分开，交换候选先后顺序，并以独立重复运行判断漂移。这个结果决定下一段工程该改哪里。[当前真机反馈](../../output/render-system-audit-20261011/r1/REPORT.txt) · [现有引擎评审](20261002-render-engine/review.md)

### 补齐确定的无效工作

优先补齐三个缺省活动状态入口，再按CPU测量结果减少重复标注、固定相机维护及轨迹线性检索。只在依赖变化时更新，保留第一帧唤醒、动画收尾与原响应时间。它们属于收益方向明确、范围可控的优化，但不能预报整体省电比例。

GPU侧先检查旧灯强度归零之后是否仍留下无贡献的shadow pass。源码仍有原生阴影配置，但只有抓帧证明该pass实际执行、贡献为零且能安全移除，才算可采用机会。不能把过去A路径的原生阴影消融金额套到当前R。

### 继续验证保留采样的球影剔除

support-full-height仍是最值得保留的算法候选：维持原样本网格、BRDF、滤波、透明度和遮挡乘积顺序，只拒绝不可能贡献的球影。首先要解释r8短测到持续的变化；如果计数器支持，再研究将不依赖接收点的球几何数据每球每帧准备一次，或构造保守分块候选表。

新组织方式必须同时证明没有错误剔除，并计入新增buffer、带宽、分支与资源成本。覆盖满台、散台、重叠影、贴库低视角、抬球、淡出和真实落袋；已通过的静态截图不能替代这些动态状态。若重复测试仍无稳定收益，就停止围绕这条候选堆叠改写。

### 再比较局部SCNProgram

如果抓帧证实台呢生成的材料代码占显著成本，可以先明确它消费的全部输入和最终可见贡献：UV、纹理色域、normal／roughness、纤维、AO、原生镜面、曝光和输出映射。再用SCNProgram只替换台呢的相关着色路径，保持其他SceneKit行为。

这比直接改constant更有控制力，但依然不是已验证无损方案。图像与连续动态先对拍，再计时；6.1%的PBR消融不等于这条等效实现必然省6.1%。若局部方案达标，就没有必要为了本次功耗目标扩大为整引擎重写。

### 由剩余限制决定是否挑战Metal

只有证实SceneKit留下无法移除的pass、资源resolve、提交或同步限制时，才提高专用Metal对照的优先级。对照首先保持同公式、同R、同资产、同像素尺寸和4×MSAA；算法改进应同时提供SceneKit版本，避免把算法收益误归因于换引擎。

完整迁移必须覆盖2D／3D、拾取、球杆与辅助线、落袋透明、停绘唤醒、缩略图及指定时间视频出口。将原台呢采样原样搬进Metal，并不会自动减少所需数学工作；编译和调度可能改善，也必须实测。[现有引擎路线](20261002-render-engine/RECOMMENDATION.md)

继续将probe和LUT离线化适合解决冷启动与换风格尖峰，优先级低于持续动态成本。用纹理缓存台呢光照或影场则涉及插值、量化、法线与视角依赖；在验证前属于新的画质候选，不能默认等价。当前模型候选已有加载与内存收益，但缺少可归因的持续GPU／功耗收益，不能以文件变小代替120证明。[模型真机报告](../../tasks/MODEL-PERFORMANCE-DEVICE-20261010.md)

## 怎样判定真正完成

历史120方案的实际呈现参考是稳定段平均≥118FPS、间隔P95≤9ms、超过12.5ms≤1%。这些是已有工程容差，不意味着每帧都准时；还应报告P99、最长帧、连续失约和触控到可见响应，不让平均值掩盖突发卡顿。App内FPS文字来自didRenderScene回调计数，不能单独用于验收。[验收原文](../../tasks/render-quality-v62/UNIFIED-LIGHTING-120FPS.md)

| 验收维度 | 需要的证据 |
| --- | --- |
| 同画质 | 同尺寸同曝光的局部与全图对照；球缘、细线、纤维、半影、号码和低视角连续运动，无新增闪烁或滞后 |
| 同物理与交互 | 同输入的碰撞／入袋／轨迹／旋转、真实时间与事件顺序；瞄准、拖球、回放、重打及相机体验保持 |
| 实际120 | 当前完整页面、合法满台、代表动态场景的实际呈现时间；不能用回调或60FPS诊断外推 |
| 持续能力 | 按既有20分钟目标分段观察，末段动态仍达标；静止时间不计作动态通过帧，也不把静止驻留判成掉帧 |
| 温感与热状态 | 未充电、亮度及环境可比，记录用户温感与系统档位；无明显发烫、无Serious／Critical；出现不适立即终止并保留失败 |
| 功耗 | 同机、同实际帧率、同场景、同方法的重复对照；另列120相对正常60使用的整场指标，不将GPU跨度换算瓦数 |
| 产品完整性 | 首次进入、切换和内存无明显回退；普通60Hz设备及最低系统正常，系统限制单列 |

后续执行沿用渐进验证：先短时确认工具与画面，再延长观察；短段已明显发热或降频，就修根因，不继续硬跑20分钟。Power Profiler在iOS／iPadOS26及以上可提供整机电池能量比例／小时和进程子系统影响；它们不是同一个单位，充电时系统功耗显示0也不代表零消耗。最后还应做脱离重型追踪的使用复核。[Apple Power Profiler说明](https://developer.apple.com/documentation/xcode/measuring-your-app-s-power-use-with-power-profiler)

当前处置保持R＋4×MSAA和既有物理／交互行为；本轮补充分析与文档，没有更改生产参数或启动手机负载。后续投入以“当前120的实际瓶颈证据→确定的无效工作→可验证的同效果局部实现”为顺序，不承诺一个现有数据无法支持的提速或省电百分比。
