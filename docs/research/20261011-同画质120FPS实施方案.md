# 同画质120FPS实施方案

2026-10-11。约束：保持当前画质、物理精度和交互效果。执行方式调整为直接制作可回退的优化版本，将验证放进每个实现批次，不再把一轮完整性能定位作为开工前置。

**采用的主线：保留SceneKit、R反射和4×MSAA，先给现有动态球影增加保守空间候选表，再消除剩余无效更新。SCNProgram作为后续局部替换路线，全面Metal迁移不进入第一版。** 这是一条可以着手实施的方案；稳定120与持续温感是交付目标，不能在实现前保证其结果。

实验与源码依据见[详细分析](20261011-同画质稳定120FPS与温升分析.md)。本方案不把已经落地的反射预计算、后台物理解算和每日静止停绘重新计入预期收益。

## 第一批 动态球影的保守空间候选表

当前台呢shader已经有球掩码和保守筛选，但筛选仍在片元路径执行。第一批把球对接收面哪些区域可能产生遮挡组织成共享空间表，减少大量片元反复排除同一批无关球的工作。

表里只保存“这个区域需要考虑哪些球”，不保存阴影颜色或低分辨率影像。因此表格较粗只会增加候选球，不应该降低阴影清晰度；最终遮挡、软影和材质仍按原生像素实时计算。

### 实现组成

| 文件或模块 | 实现内容 |
| --- | --- |
| 新增 `ClothShadowCandidateGrid.swift` | 根据灯、接收区域和球快照生成保守单元候选；每单元保存球ID位掩码，沿用现有最多32球的掩码能力 |
| `MobileTableRendering.swift` 的接触参数更新 | 从本帧同一份presentation球位、球高、透明度及隐藏状态生成球uniform和候选表；一起提交，避免一帧错位 |
| `MobileReferenceLighting.swift` 的直接球影路径 | 增加候选表查询，只收窄原有遮挡候选；实际球影求交、过滤及累乘顺序保持 |
| 场景配置 | 增加场景级候选开关，原R路径完整保留；无效表、未知接收区域或超出能力范围时回退原计算 |

初版只在球、灯或接收几何变化时更新空间表。球不动、相机转动时复用世界空间候选表；视角相关BRDF仍然逐帧计算。上传资源采用不会覆盖GPU在用数据的缓冲策略；保留原有同帧阴影提交时序，不在渲染线程增加GPU完成等待。

### 必须保持的算法边界

1. 原 `shadowPossible` 继续决定每灯32／4样本档位；不能用某个格子有候选球就切换档位，否则会改变画面。
2. 新表只用于缩小遮挡循环候选；保留原灯样本网格、滤波半径、BRDF、透明度及按球ID的累乘顺序。
3. 包围范围覆盖球半径和软影滤波，不只使用硬阴影投影。
4. 不将接收面一律视为二维台呢。初版可以仅加速已验证的台面高度范围，库顶、台面以下及其他未覆盖接收点走原路径；腾空球范围须保守处理，不能漏影。
5. 边界取保守方向；不确定时多保留候选，不能错误拒绝。世界空间单元查询不做会混合位掩码的纹理过滤。

这种组织有机会扩大现有保守剔除收益，但不能把r5约7.7%至20%的短测成绩当作新表收益，更不能再叠加一次。r4曾证明循环外提未必更快，所以初版控制新增表、读取和寄存器成本，单独比较候选开关。

### 本批交付

先在桌面验证零错误剔除、边界回退、回放跳转和同帧更新，再用同输入的原生图像与动态序列核对球架、散台、贴库、低视角、腾空、淡出、真实落袋和重叠半影。通过后交付一个可开关的完整页面版本；随后验证实际120呈现及短时成本，再逐步延长运行。

如果新增查询／上传抵消收益，候选留在开关后，不在它上面继续堆叠微改；进入下面的局部材质路线。

## 第二批 消除剩余无效更新

这批可以独立实施，主要改善整场训练平均消耗及CPU余量。

| 修改位置 | 实现内容 | 保留条件 |
| --- | --- | --- |
| `DrillSceneView`、`BallExtractionView`、`BatchBallExtractionView` | 显式提供播放、拖动及过渡活动状态，补齐静止休眠 | 拖球、节点动画和首帧唤醒完整；不把全局nil默认直接改为false |
| `AngleSceneView` 的辅助维护 | 按相机、尺寸、内容版本更新标注与固定相机布局，跳过依赖未变的工作 | 球和相机需要运动时继续120更新；不降低可见辅助内容跟随频率 |
| `TrajectoryRecorder` 局部轨迹查询 | 建立保持相同区间选择的查询索引；回放跳转时正确复位 | 保持原采样公式、边界优先级、碰撞／入袋事件及旋转精度 |

每日主入口已有静止停绘，这批不能宣称重新获得一次相同收益。物理解算保持现有模型与后台执行，不降低精度，也不将60帧位置重复播放成120。

## 第三批 台呢材质的局部替换

如果前两批仍达不到目标，制作只替换台呢着色的SCNProgram版本。场景树、相机、物理、球反射、房间、球杆与交互继续复用现有实现。

第一步明确并复现台呢全部输入与最终可见贡献，包括UV、贴图色域、法线、粗糙度、纤维、AO、原生材质贡献及输出映射。保持原光照和阴影公式，在这个基础上减少生成材质中的无用计算。

不能直接把 `.physicallyBased` 改成 `.constant` 当作本批实现：已有实验出现变暗和纤维损失。也不能承诺消融中约6.1%的差值全部可收回。原路径与新路径使用同一场景开关比较，图像、动态和实际成本都通过才采用。

## 第一版明确不采用的办法

- 不降低原生分辨率、4×MSAA、纹理质量或物理精度。
- 不关闭反射、接触暗部或球影。
- 不用低分辨率阴影贴图代替当前逐像素球影。
- 不把球影更新降到60Hz而让球120Hz移动。
- 不采用已有画面变化的RS阴影或减少BRDF采样候选。
- 不先迁移整个引擎；只有局部路线仍受到明确框架限制，才另行比较同算法Metal版本。

## 每批怎样结束

验证与实现一起推进，不再另开一轮漫长定位。每批依次交付：可回退代码、同输入画面对照、完整页面操作结果、实际呈现与持续温感结果。已有历史120方案的呈现口径继续作为参考：平均至少118FPS、P95间隔不超过9ms、超过12.5ms占比不超过1%，同时报告长帧和连续失约，不能只看App中的回调FPS数字。

持续验收按既有20分钟目标，正常连续击球和自动镜头为主场景；静止段与活动段分开统计，末段动态仍须达标。未充电、亮度与环境可比，用户没有明显烫手感，且不进入Serious／Critical。先短段确认，出现明显发热就保留失败并改实现，不硬跑到规定时长。

当前已完成的是实施方案，尚未修改生产代码。首批实际改动范围锁定为“候选空间表＋现有shader接入”，并行补齐三个入口活动状态；用这一版的真实结果决定是否进入SCNProgram。
