## 0. 背景与诉求

产品是教学性质。当前反解器只回答「解是否存在」，不建模「人打起来难不难」。用户核心观察（均已在物理与代码两侧验证）：

1. **母球不吃库时，横塞（spinX）对走位几乎无贡献**——squirt 已被瞄准解内部补偿，用户感知不到收益，却承担了最难的杆法（挤偏/弧线/随力度变化的补偿）。
2. **很多吃库走位可用高低杆（spinY）替代横塞**，前者对业余玩家容易得多。
3. 结论：求解不应只考虑「能否找到解」，还要考虑**执行难度与容错度**，并把替代关系透出给用户（本身是教学内容）。

### 现状缺口（代码事实，已核实）

| 维度 | 现状 | 缺口 |
|---|---|---|
| 吃库数 | ✅ 桶 + `maxCushions` 预算（`PositionPlaySolver.swift` L46–49、L129–139） | 无 |
| 横塞 vs 高低杆 | ⚠️ 对称范数 `spinMag = √(x²+y²)` 等权（L379） | 横塞难度远高于高低杆；`spinX=0.3` 会赢过 `spinY=0.4` 的纯低杆解 |
| 0 库解带横塞 | ❌ 不特判 | 纯增加难度、零走位收益，应换用同桶无塞代表 |
| 塞幅分档 | ❌ 连续值 | 半颗塞与极限塞难度差一个量级 |
| 力度极端性 | ❌ 无 | 力度扫到 6 m/s，大力杆瞄准精度骤降 |
| 进球本身难度 | ❌ 无 | 薄球+远距离时解「存在」但人打不进 |
| 执行容错度 | ⚠️ 仅 margin（结果空间余量） | 参数空间敏感度未量化（「悬崖解」vs「平地解」） |
| 呈现 | 每吃库桶一个代表 | 用户看不到「难但准 / 简单但差一点」的替代关系与难度标签 |

## 1. 红线约束（每批次共同遵守）

1. **不加密搜索网格**：难度感知只改「偏好 / 挑选 / 呈现」层，禁止为多出无塞解而加密 spinX/spinY/velocity 网格（会吃掉 B0–B5 提速）。若实测纯高低杆解常被粗网格漏掉，单独立项、单独测基准。
2. **性能验收**：每批次改动前后跑 `QiuJiTests/PositionPlaySolverTests.swift` 的 `test_perf_productionParams_printsWallClock`，差异须在噪声范围内（E3 前置剪枝应更快）。
3. **画面=物理不变**：上屏解仍全部经引擎复核物化，难度层不触碰复核流水线语义。
4. **几何/坐标类改动**（E4 切角）动代码前遵循 `geometry-spatial-reasoning` 技能。

## 2. 待拍板项（开工前确认，已有建议默认值）

| 项 | 建议默认 | 说明 |
|---|---|---|
| 难度加权比 wX : wY | 2.5 : 1 | `effort = wX·|spinX| + wY·|spinY|` |
| 力度惩罚阈值 | 4.0 m/s | 超过按超出量线性加罚 |
| 塞幅分档线 | 0.15 / 0.3 / 0.5 R | 微塞 / 半颗 / 极限三档 |
| 同桶有无塞解时横塞解的处理 | 换代表（桶内本就只出一个代表） | 教学/新手模式下配合 E3 预算彻底不出横塞 |

## 3. 批次拆解

### E1 — 共享难度比较层（基准批次，先做）

**范围**
- 新建 `DifficultyModel`（建议放 `QiuJi/Core/PositionPlay/`）：加权 spin 范数 `effort(spinX, spinY)`、力度惩罚、塞幅分档；常量集中可调。
- 替换上表 5 处排序/比较点的对称范数为加权范数 + 力度惩罚（统一走 DifficultyModel，一次改、五处受益）。
- **0 库桶特判**：情形 A 桶内（`topPerBucket`/`settle` 挑代表路径 L420–460）当 `cushion == 0` 且桶内存在 `spinX == 0` 的合格候选时，无塞候选优先做代表（可替代性以同桶扫描结果为证据，不做理论判断）。
- 落点场景 `closerFirst` 调整：距离仍第一序，但 tie-break 换加权范数；是否引入「距离容差内难度优先」由实测决定，默认不引入（不改需求语义）。

**依赖**：无。
**完成标准**：
- 单测：构造「spinX=0.3 vs spinY=0.4 同桶」用例，断言纯高低杆解胜出；0 库桶横塞换代表用例。
- 既有回归测试（`PositionPlaySolverTests`、`SnookerSolverTests`）全绿；预期部分快照断言需按新排序更新，逐条人工确认属预期变化。
- perf 基准对比在噪声内，输出真实数据。

### E2 — 难度评分与标签透出

**范围**
- `PositionPlaySolution` 增加 `difficultyScore: Double` 与 `difficultyTier`（枚举，如 中杆即可/需高低杆/需横塞/极限塞）。
- 三处装配函数（`makeRegionSolution` L666、`makePassSolution` L965、`makeSnookerSolution` L1300）计算并填充；summary 文案追加难度语义（如「需半颗左塞」）。
- `SiluTrainerViewModel` 文案拼装（L527–533）与解切换 UI 透出难度标签（具体展示样式：待定位，实现时与现有解序号/进阶标记样式对齐）。

**依赖**：E1（DifficultyModel）。
**完成标准**：每个解带 tier 与评分；UI 截图确认标签展示；构建+回归全绿。

### E3 — 塞幅预算 maxSpinTier（优先+兜底）+ 教学模式前置剪枝

**范围**
- `SearchParams` 增加 `maxSpinTier: Tier?`，仿 `applyCushionBudget`（L129–139）做后处理「优先+兜底」，兜底解标记（仿 `beyondCushionBudget` L115）。
- **前置剪枝**：预算为「无横塞」时直接裁剪 `spinXValues`（combos 从 ~13 → ~5，扫描提速约一半），仅当预算内无解才回退全网格重扫——回退路径保「绝不因预算给出无解」语义。
- `SiluTrainerViewModel` 接入开关（仿 `basicPositionOnly → maxCushions` L458 模式）。

**依赖**：E1、E2（tier 定义与标记字段）。
**完成标准**：预算内有解只出简单解；无解兜底展示并标记；剪枝路径 perf 输出显示提速；回归全绿。

### E4 — 进球难度（切角 + 球距）纳入评分

**范围**
- 从 `ShotPredictor.prepareAim` 的瞄准上下文取切角与母球-目标球距离，折算进 `difficultyScore`（薄球+远距降权/标注，不改硬约束——解仍返回，只影响排序与标签）。
- 分档阈值（如切角 > 75° 标「薄球」）进 DifficultyModel。

**依赖**：E2。遵循 geometry-spatial-reasoning（坐标契约回显后再动代码）。
**完成标准**：薄球用例排序靠后且带标注；回归全绿；perf 在噪声内（评分仅对最终 2–4 个解计算）。

### E5 — 扰动容错分析（L3，可选开关）

**范围**
- 对最终代表解做 ~6 次参数扰动（瞄准 ±0.5°、力度 ±8%、打点 ±0.05R）解析 rollout（复用 `AnalyticShotRollout.evaluate`），统计「扰动后仍进球且停区保持」比例作为容错度。
- 容错度进 `PositionPlaySolution`（字段名待定）与 UI；教学模式排序在同吃库桶内容错优先。
- 做成开关（默认关或仅教学模式开）；扰动数值与判定口径写进 DifficultyModel 常量。

**依赖**：E1、E2。
**完成标准**：构造「悬崖解 vs 平地解」用例（力度小扰动即换吃库拓扑 vs 不换），断言容错度区分二者；开销实测 <2%（对比 perf 基准输出真实数据）；回归全绿。

## 4. 批次依赖图

```
E1（共享比较层）──→ E2（评分+标签）──→ E3（塞幅预算+剪枝）
                        ├──→ E4（进球难度）
                        └──→ E5（扰动容错）
```

E3 / E4 / E5 相互独立，可并行或换序；每批一次会话完成并验收。

## 5. 与性能优化方案（B0–B5）的关系

- 全部改动落在排序/挑选/装配层，扫描与复核流水线（B1–B5 产物）不动；E3 前置剪枝与性能优化**同向**（更快）。
- 唯一新增计算是 E5 扰动 rollout（每次求解 ≈20 次解析 rollout，<2%）与 E2/E4 对最终解的评分（零级别）。
- 每批以 `test_perf_productionParams_printsWallClock` 真实输出为准，禁止凭估计宣称「无影响」。
