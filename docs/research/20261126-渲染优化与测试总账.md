# 渲染优化与测试总账

截至2026-11-26（北京时间）。汇总历次渲染性能、资源、加载与交互更新优化，以及影响结论的失败实验。依据项目原始报告和本会话真机记录；不是一次重新执行的全量回归。表中的“已接入”表示对应阶段的生产交付状态，不能自动等同今天每个页面、每个机位都命中该算法。

用户补充的重要历史反馈：**最后一轮优化全部应用后，亲自使用时很平稳、也不发烫；近期再用出现发热。** 这是有效的使用体验线索。目前缺少那次良好体验对应的精确安装包和同步采样，不能用较早的发热记录否定它，也不能只凭旧优化仍接入就排除后续回退。

## 4. 当前能据此判断什么

1. 确实有多层真实优化交付，既包括CPU／空闲／加载，也包括GPU算法和资源；不是只做了一次LTC，也不是研究编号对应的每项实验都应用了。
2. 不能把−13.6%、−40%、−19.7%、−7.5%、−4.8%、−30.7%相加或连乘为“整个App总收益”。它们的设备、基线、场景、视角、统计窗口与测量对象不同，部分包含前一层优化。
3. 当前休眠路径在已测每日清台状态仍有效，原台呢优化没有简单丢失；这不排除后续新增工作抵消收益，也不排除其他状态的回退。
4. 11月23日完整预览调度15→24Hz并扩大拖动时完整预测范围，是已核实的CPU工作策略变化。物理求解在CPU执行；节点更新可能间接影响渲染，但当前约32%CPU份额不能解释GPU为何90%以上。
5. 当前尚缺最后良好安装版本的身份、旧新同球形／同机位／同显示配置对照，以及库边材质、相机与轨迹更新的独立GPU成本。不能把“没有旧量化数据”写成“用户的良好体验不成立”，也不能把推测写成已确定根因。

### 新增库边效果的具体检查点

当前[MobileRailAppearance.swift](../../CuePhys/Core/Scene/MobileRailAppearance.swift)的`finish`在`p.y>0.8005`范围调用`v62PanelDiffuse(p,railSoftNormal)`与`v62PanelDiffuse(p,n)`求差，用于保留已确认的库鼻过渡外观。这是TaiNi高于台面的部分，不是整个台面或Wood木材质。两次调用的法线不同，并非可以直接删掉其中一次的等值重复。

该函数仍走矩形灯裁剪、归一化与`atan2`解析积分。[StaticClothIrradiance.swift](../../CuePhys/Core/Scene/StaticClothIrradiance.swift)的C1只替换主照明的一处调用，没有改写函数定义；[MobileReferenceLighting.swift](../../CuePhys/Core/Scene/MobileReferenceLighting.swift)在C1/H9/LTC转换之后才注入库边效果。因此新增的两处调用绕过了固定灯查表入口。与此同时，同一库边分支两次计算相同的几何法线，但编译器可能已合并，不能按源码次数推断实际GPU指令。

这使库边新增积分成为优先做增量对照的明确候选，尚不能判定它占比大或造成发热。尤其库侧法线可能不满足C1的全灯可见条件，直接替换成查表可能仍回退，或需要新的质量验证。下一步应复用原夹具，保持当前库边外观、机位、分辨率、MSAA和帧率，对照积分复用／预计算候选；先确认编译后实际成本和像素差异，再做手机同条件验证。原机位LTC域外的台呢路径仍是另一重点，不能只通过放宽LTC门槛获得未经验证的收益。

24Hz完整轨迹预览是已知CPU工作量变化，单列15/24Hz诊断与结果更新归因；当前CPU样本不能归为库边GPU耗时。本节只补充源码审计，没有执行新GPU对照或修改生产代码。
