## 最新具体方案：两种3D视角与受约束轨道

用户提出的方向值得继续：第三人称以轨道进度`s`与绕桌方位`θ`作为两项控制，眼位由同一函数`E=γ(θ,s)`生成；上下滑动进退，左右滑动绕桌。它减少眼高、俯角、距离、FOV各自变化的控制耦合。上下对应哪一方向仍是交互选项，本报告建议上滑接近/放大、下滑后退/缩小，不作为已批准约定。

**轨道建议：**以固定桌面观察中心作为默认基准，眼高保持相对地板稳定，FOV先保持稳定，朝向平滑地围绕桌面构图。轨道按实际矩形球桌、房间和HUD生成，不要求圆形或直线；各方位的近/远边界由同一规则确定。前后进退带来的透视变化属于真实dolly，不能称与只改FOV的光学放大相同。最近端可以允许局部裁桌，最远端保留全桌上下文，具体取舍由观看任务确定。

固定世界眼高不等于屏幕上的地板位置不动。接近桌面且继续朝桌心看时，俯视角会变化；若还要求屏幕地面/桌沿保持位置，需要额外构图约束，可能与近景或固定FOV冲突。因此建议先将舒适性定义为眼高稳定、朝向平滑、无突跳，再决定是否需要屏幕锚定。

**两模式的横向含义建议：**第三人称绕桌移动；第一人称优先固定当前站位/眼位转头。若第一人称也绕母球移动，那是身体换站位，透视与遮挡会变化，应作为另一明确选择。转头或换站位均不应无声改变击球方向；回到杆轴瞄准的动作需明确。第一人称是否允许上下进退/转头俯仰、pinch是否共用第三人称轨道，以及选球/选袋会否移动第三人称观察中心，仍待产品选择。

**渲染影响：**相机域更受约束，可以生成确定的轨道视线集合，用来限定角响应拟合与空间误差，但两维相机不等于两维BRDF。接收位置、微法线、roughness、联合球影及动态第一人称站位仍是响应输入。轨道进退不改变V内容，放大会改变所需精度；绕桌会改变可见接收面和屏幕覆盖。低机位第一人称的掠射、高光、库边/袋口和球面反射仍需适用域外的原积分或高频修正，不能因删一个预设就宣称已大幅节能。

常规第三人称可沿轨道规则直接求姿态，不必为每个球形搜索完整观察机位；这有望降低未来求解与维护成本，并非当前CPU/GPU毫秒证据。轨道边界需连续，不能按方位分别拟合后产生跳变；若某处不可行，不靠突然抬高/FOV切换掩盖问题。第一/第三切换仍从实际姿态出发，按同帧时钟与所有权提交。

## 2. 从观看任务到计算方法

联合设计的顺序是：**观看目的 → 必需主体与可读性 → 允许的眼位/镜头/运动 → 对应渲染表示及误差 → 同帧提交。** 当前相机类不是新的相机语言真源；它只是现有实现与迁移参照。

| 观看任务示例 | 相机需要回答 | 渲染需要回答 |
|---|---|---|
| 读整盘关系 | 哪些球/袋/路线必须看清，保留多少上下文 | 床面覆盖和近影片元数有多大，世界场生成与读取是否值得 |
| 阅读当前一杆 | 两球、真实袋口、必要路线如何避开其他球/库/HUD | 哪些床面/库顶/袋口必须保持真实接收几何，如何保证接触影和球面反射 |
| 杆后瞄准或击球 | 眼位与杆轴的关系、允许怎样转头，何时离开此视角 | 掠射微法线/高光、near clipping和高频响应的有效域 |
| 手动细看 | 手势从哪个实际姿态接管，自动相机何时可重新介入 | 放大后的世界/屏幕精度变化，当前帧如何细化或回原公式 |
| 击球过程与结果阅读 | 是否切镜、何种事件触发、运动路径及中断规则 | 同一呈现时间下球/影/相机一致，不能用旧场或异步补影 |

不能从名称“全局/第一人称”直接推出便宜或昂贵。高机位可能显示更多床面，低机位可能包含更多非平面接收面；实际视线、屏幕覆盖和材质域才决定代价。

## 3. 分开职责，共享必要事实

建议先明确职责，不先制造一套庞大新框架：

1. **观看意图与事件政策**决定主体、观看任务、自动/手动所有权、转镜触发及恢复行为。产品语言在这一层表达，不嵌入shader或某个引擎类。
2. **取景求解与运动控制**把意图变为eye、orientation、lens与可执行安全路径，负责当前主体/HUD可读性、手势和连续性。新的取景方法可以替换旧CameraRig内部策略。
3. **帧采样与宿主适配**冻结实际显示相机矩阵、投影、viewport/裁剪范围和同帧对象状态；投影、拾取、锚定与标签消费同一最终状态。
4. **渲染表示选择**依据当前接收域、视线及误差要求选择世界场/角基底/原积分，负责资源和GPU顺序。缺少资源时仍用本帧直接公式，不能擅自改变相机取景。

相机可见性和灯光遮挡可以共享稳定对象ID、实际可见几何与资产版本，但算法不同：前者是眼到主体的射线，后者是接收面到灯样本的射线。不能共用一份“可见度结果”，也不能把相机裁剪外的球从球影候选中直接删除。

## 4. 联合契约需要哪些字段

优先在既有`RenderFrameSnapshot`建议中加入明确相机部分，而不是为了联合设计先拆一批跨模块接口。

| 契约 | 最小内容 | 失效/所有权 |
|---|---|---|
| 观看请求 | subject IDs、角色、scene/request revision、HUD/viewport、允许机位/镜头、可读性目标、用户接管状态 | 当前意图变化或影响该任务的几何/HUD变化才求解；非逐帧无条件搜索 |
| 取景结果与路径 | eye/Q/lens、质量/受限原因、请求版本、owner epoch、路径、实际接管点 | 结果提交同时核对请求与所有权，迟到结果不夺回手动控制 |
| 实际相机帧 | view/projection矩阵、正交/透视类型、实际viewport/裁剪、当前时间、session/generation、camera revision | 每帧最终姿态；不是尚未到达的目标姿态 |
| 渲染依赖 | blocker revision、receiver/rig/layout/algorithm key、材料/显示参数版本 | 相机内容变化不自动失效V；表示精度与材质响应分别判定 |

真实球心/高度/有效opacity负责blocker变化；只有相机转动或球自转，V内容可以复用。相机拉近、纹理LOD改变、掠射则可能让当前表示精度不足。将“内容版本仍有效”和“表示满足当前误差”作为两个判断，不能混成一个sceneDirty。

观看求解不应在每次CADisplayLink内对所有候选重跑。自动取景在明确意图或相关约束变更时发纯值请求，连续运动每帧按已有时间政策推进；若未来语言确实需要追踪运动主体，应明确跟踪更新与重规划触发，不能默认所有镜头都是静态解。

## 5. 镜头域决定角响应压缩能否成立

压缩契约至少包括：接收几何域、实际视线范围/最小n·v、微法线/roughness域、镜头与投影范围、像素对应世界尺度，以及E/S线性输出误差。当前旧35°、0.95秒或某个固定眼高只是实现事实，不作为新语言的固化参数。

低机位改变n·v与镜面响应，不直接改变n·l的灯光horizon；纹理LOD可能改变实际微法线，因此条件性漫反射方向矩仍需证明法线锥。仅按高机位拟合的角基底不能声称覆盖杆后掠射；不能用一张平均阴影图代替完整方向遮挡。

世界V场的cell证书可以跨相机帧复用；传播到E/S的界还依赖当前材质响应。若采用覆盖全部允许镜头域的保守界，其范围需要在新语言定义后冻结。转场经过的中间机位也在域内，不只检查两端。超出表示域时当前帧走原积分；连续精度切换和资源替换需要独立契约，不能显示旧阴影补帧。

渲染器无权用拟合域反向限制镜头。当前表示不足时回原公式或明确重建表示，不能擅自抬眼位、收窄FOV、取消近景或手动自由度；观看能力的改变只能来自新语言的产品选择。

固定房间probe通常不因相机位姿改变而重捕获，但新视线会暴露不同反射方向与近距离误差。若新语言还改变曝光、景深、bloom/SSAO等画面处理，需要单列实际依赖与成本，不能把它们都当“只改镜头”。当前材质高光映射已读取曝光（`MobileReferenceLighting.swift:575–589`），曝光变化也不能只改SCNCamera就宣称所有材质响应一致。

## 6. 同帧与运动事件

一份最终呈现快照必须让实际相机、球/杆、阴影和屏幕交互保持一致。DisplayLink是唤醒源；仿真时间、回放时间、呈现尾段和相机运动时间有明确映射，不能把所有时钟强行等同或由GPU completion决定转镜。

剧情/训练事件按本杆有效呈现时钟触发；当前capture规则只是例子。新语言若改变站起/跟踪/复盘时机，由事件政策决定，渲染器不提前消费最终进袋预测。手势接管、重开、重打、暂停/seek、2D往返各自撤销旧代次，实际姿态采样而非目标姿态接管。

事件按有效时钟区间消费并核对杆次/generation，使用稳定event ID与消费游标保证一次语义。GPU背压跳过某次draw时，下一有效取样必须处理该区间跨过的有效事件，不能漏转镜或重复触发；事件消费不要求恰好绘制其时间点。暂停及seek的事件重放/抑制由观看政策单列，不能将“向前seek”无条件当正常经过所有事件，也不依赖GPU completion或固定墙钟延迟。

若换受控SCNRenderer，需保证相机运动与SceneKit动作各推进一次；当前屏幕锚定、2D fit、project/unproject、hitTest和标签不能继续读取未同步的旧SCNView。新相机语言允许改变政策，但当前有效状态与输出矩阵的契约必须明确。
