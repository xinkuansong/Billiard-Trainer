# 真机性能与独立反方评审

2026-10-02（Asia/Shanghai）。角色：Test Engineer / QA Reviewer。仅研究审计，不是 Phase 放行。本轮读取真实代码快照、SDK能力报告、历史原始分析JSON和项目验收真源；未改生产代码/资产、未加依赖、未构建、未安装、未运行真机负载。依据 cursor-project-adapter、50/55角色规则和 ios-device-performance。没有用同模型多数共识作为验证。

## 1. 独立判断

**三份报告的近期路线可附条件接受：优先验证当前 SceneKit 中的领域算法、资源准备与宿主调度；专用 Metal 保留为可证伪的挑战者。不能接受“SceneKit已是效果最好/能耗最低”，也不能接受“纯Metal一定是最终方案”。** 当前没有跨引擎、同画质、完整页面和真实能耗对照，能给的是验证顺序与能力适配判断。

最强反对意见有两面：继续SceneKit可能长期困在黑盒与弃用生态，失去显式pass/资源/呈现的机会；全面Metal可能把昂贵的原积分原封不动搬过去，增加维护、画质误差和线程资源问题却几乎不省电。两面都必须用受控结果推翻或支持。

真实问题不是泛型框架速度排名。应分别问：①相同效果/输出/体验，谁做的工作更少；②相同能耗和时间预算，谁的可感知效果更好；③完整产品功能、维护风险和支持版本，哪条路线值得投入。三个答案未必属于同一引擎。

## 3. 对各角色的实质异议

### 管线报告

1. **P0 activity补齐有价值，但不能用作每日发热的既定主因。** 要求报告分别给共享非每日覆盖、每日idle与每日动态三个账单。常驻动作、重建、无效写入须有trace，而不是一律设置false。
2. **SCNProgram是纯Metal推荐的强反例。** 若只替换台呢vertex/fragment、去原生PBR尾部即可达标，全面迁移的边际价值显著下降。SceneKit modifier→SCNProgram→SCNRenderer+MTKView→纯Metal按控制需求逐级比较，禁止跳过能覆盖热点的中间方案。
3. **相同积分不保证相同编译成本，但也不保证Metal更快。** 支持GPU代码/寄存器活跃区、绑定、pass/attachment、带宽/tiler限速证据；“数学相同所以毫秒相同”和“控制更多所以省电”都是过度推断。必须辨认真正消失的工作与新增成本。
4. **算法轴独立。** support表、缓存shadow field、LTC、S/RS属于不同程度的计算/采样/模型变化。必须同时提供优化SceneKit中的同算法版本，防止把算法收益归为换引擎。
5. E2精确buffer binding方法最低iOS9，不能沿SCNProgram/SCNShadable类iOS8标注；主控已要求修正。这不影响17可用结论，但API可用性须精确到方法。

### 资产报告

1. **约95%源面复杂度在桌体不证明应先减面。** 若当前fragment ALU限速，LOD可能只改善加载而不改变持续成本。反之若真实tiler、buffer或material submissions占高比重，则旧shader热点优先级应改，不能由旧room-off小收益否定资产路线。
2. **清理被覆盖贴图只有条件性收益。** UIImage/URL retained不是上传、解码或驻留证据；必须分别量解析/CPU峰值、纹理allocation与GPU带宽。保留legacy/离屏所需母版。536MiB不是内存验收基线。
3. **离线probe对持续热不是同幅收益。** 首次neutral/room双预滤、style cache miss需时间线验证。热进入之后若不运行，该优化不能解释击球持续热；如冷准备足以解决用户操作问题且动态达标，应停止为此迁移。
4. **资产时点尚未获批与当前获批区分。** assets.md读取时8×6是候选；当前PROGRESS已记用户选定8×6并有后续集成。最终比较应重新冻结获批的模型、贴图、相机/灯、包体哈希；本轮早快照不能冒充后续获批完整运行版本。
5. **反射失效键应只包含实际输入。** 把所有主题/曝光均塞缓存键可能制造无效重烘。要求说明哪些输入确实参与probe radiance、哪些只是最终输出变换；正确依赖图比宽泛哈希清单更重要。

### 引擎报告

1. **P1“对比原A”对每日场景有误导风险。** A共享reference与R每日生产分开建基线；09-27实验A1只是R上的相机/台呢reference开关，不是shader profile A。建议名称写SCN-shared-A、SCN-daily-R及R-camera-ref，避免重名。
2. **RealityKit17不推荐统一替换是需求能力缺口，不是能耗失败。** 正交与确定性离屏缺口是具体淘汰理由；如果用户今后改变系统/出口需求，应重评，不能永远按本轮淘汰。
3. **Filament要保留有竞争资格。** 当通用材质、透明处理、asset pipeline与跨设备稳定性维护成为主要成本时，成熟引擎可能优于专用Metal。需实际项目构建和同画质验证，不能以本轮三个模型同意SceneKit作为淘汰证据。
4. **SceneKit弃用可独立触发兼容性规划，但不证明当前低耗迁移。** 若新OS真实出现不可修复正确性/工具链/驱动问题，迁移可以由维护风险启动；应诚实说明不是能耗赢家。
5. **功能出口必须算清。** 一页Metal保留SCN视频的过渡方案要计算双纹理缓存/材质/测试维护，不许把单页demo胜出写成共享引擎已适配完成。

已向管线、引擎代理发出交叉问题，资产问题交由主控要求回应。管线在§8、引擎在§9已明确接受每日R/非每日activity分流、SCNProgram/SCNRenderer达标则停止全面迁移、纯Metal以残余可测受限项触发；引擎强调Filament排序可被维护/实装成本推翻。评审核对追加文本后认为它们收窄了首轮结论，但它们仍不是性能验证。资产在“交叉讨论、状态更正与可执行停止线”附录已回应并经评审阅读：纠正房间当前已选定试用，保留原08:17资源统计时点；撤回全部主题/曝光泛列缓存键，区分实际捕获scene/有效材料与最终输出变换，说明fragment highlight headroom例外；动态接触uniform残留明确为未测风险，提出规范捕获与访问顺序验证，不宣称已发生bug。资产也接受局部路线达标即停止当前能耗驱动的全面Metal重写。三路回应状态已收口，相关实测与原型仍未通过。回应是补证据和修改条件，不是多数表决。

## 4. 公平实验：两组不同问题

以下均为后续建议，未运行。本轮不要求手机操作。

### 组I：同画质降低成本

- 冻结共同数值帧记录：球位/四元数/opacity、杆姿、六袋角色、袋内/回球状态、相机projection/view、光位/颜色、room/桌资产哈希、输入时间与像素输出。物理预测单独运行并冻结，不重复随机开球影响比较。各引擎用同clock采样，不用墙钟等待模拟指定帧。
- 以当前每日R为主，以共享A为另一套需求基线，禁止混池。记录普通Release/Profile优化与诊断instrumented同版本；正式默认/Pro120等策略另测，不能用只限60的结果代表实际120。
- 比较SCN原宿主、优化SCN、SCNProgram、必要时SCNRenderer+MTKView与纯Metal；任何算法版本至少在SCN和Metal各有一版，形成宿主×算法对照。台呢原近影64总采样、同支持/可见度公式、同R反射作为第一个控制版本。
- 相同drawable像素、输出色彩、曝光/tonemap、4×MSAA、纹理/几何/相机、活动请求帧率与可见对象。新引擎内部实现不必位相同，但最终认可的效果不得削弱；公式等价小改保留逐像素验证，完整新渲染器用局部质量、连续动态与用户认可共同判断。
- 先实际scene验证、shader编译/替代色检查、动态同帧阴影检查，随后孤立renderer测成本、真实完整页测呈现/响应/能耗。孤立赢而完整页不赢，只能保留局部研究结果。

### 组II：同预算提高效果

- 冻结每台设备的GPU/CPU截止、活动60Hz、长时能耗/热预算、驻留与启动目标；每候选在这个预算内优化画质，算法/抗锯齿技术可以改变，输出尺寸仍固定，变化逐项披露。
- 对照用可信App参考和用户未满意点：球面树脂体积/反射灯板、台呢纤维与近影、皮革内壁、号码旋转与六袋识别、房间照明和运动稳定。盲审同机位原像素静帧及连续动态，不以“更锐/更亮”代替真实感，不让全图均值掩盖小球影条带。
- 报画质收益和预算占用，不能把组II的新阴影算法、较低采样或不同AA收益倒算到组I的框架收益。达标但明显降效的候选不属于组I同画质冠军。

本轮不擅定“迁移至少20%”等新数值，因为尚无当前R噪声及真实维护成本。可在基线采集后、候选结果揭示前冻结实用收益阈值；它只能加严选型或明确独立新决策，不能放宽v62/09-27已有底线。

## 6. 功耗与温升的可核验口径

2026-10-02已读取Apple官方全文及本研究保存的官方Markdown。[Power Profiler](https://developer.apple.com/documentation/xcode/measuring-your-app-s-power-use-with-power-profiler)：仅iOS/iPadOS26+；系统能耗是电池能量比例/小时，应用power impact是进程子系统指标，模型间数值不可直接比较；充电显示系统0不能作为零耗电。连接Xcode影响sleep，应另做脱离工具的低扰动复核。官方指标不是未经校准的应用瓦数。[本地全文](primary-sources/measuring-your-app-s-power-use-with-power-profiler.md)

- iOS17底线设备仍需真实渲染兼容/性能与持续使用验证；不能因新Power Profiler缺失而假称低能耗，也不提升最低系统。可用旧指标则明确代理及局限。
- 每个型号内部比较相同方法；整机电池比例包含display/system/network，应用impact另报，不相加或互当单位。GPU interval union、command-buffer span、CPU工作量分别是代理，不能换算J/W。
- 若确有经过验证/校准的整机电能量，按相同时长/操作数/实际呈现输出报能量/任务和功率；不能从短时电池百分比反推。没有它也可报告同机功耗指标方向，不命名最低瓦数。
- 通过局域网不意味着拔掉有线或MagSafe；后续执行按ios-device-performance确认未充电、正常温感/可操作，已有当轮确认沿用。记录亮度、初始电量/thermal、环境温度、外壳、OS/device/build、trace开销。
- 图像录像、重型GPU捕获和低扰动能耗分别运行，保证输出质量同样已经验证。出现用户明显发烫或严重热状态停止加压，保留原因和缺失窗口，不重启补造完整排名。

## 7. 什么会改变推荐

**留在SceneKit并停止全面迁移**：局部SCNProgram/SCNRenderer控制或资产准备/LOD解决真实瓶颈，完整页画质、呈现/响应、长期性能与能耗目标达成；纯Metal额外收益不稳定、仅来自换算法或删功能。长期保留接口/资产可迁移性规划，不因此无限做prototype。

**触发最小Metal挑战**：优化SCN后残余热点确为内部不必要pass/绑定、资源驻留/隐式同步、可测调度或呈现黑盒限制；或者同算法在SCN中受到无法解开的实际管线限制。用同公式最小原型证明成本差异，再用同算法SCN/Metal双向对照验证。动态阴影如果才是热点，先做算法研究而不是由它自动触发迁移。

**触发实际迁移决策**：最小原型在完整App配对有稳定、可解释净收益；兼容17、低机位/六袋/拾取/两投影/确定性导出与所有生命周期完整；启动/资源/热态通过；双管线维护与原生输出差异有明确成本与出口。核心正确性或SceneKit生态风险可以另立维护迁移原因，不能伪称已测低耗。

**Filament重新进入**：纯Metal须大量自研通用PBR、透明、资产/设备兼容设施，实际维护风险超过领域定制收益；对同夹具完整prototype证明无需不可接受近似/双出口。**RealityKit重新进入**：系统/出口边界由用户明确改变并经能力验证，不只看18+接口存在。

**立即停止或拒绝晋级**：未验证present身份、B窗口缺失/基线漂移未控、画质削弱、最低系统缺口、漏活动唤醒/动态残影/袋内错序、泄漏持续增长、功能不完整、明显发热。先修测量/正确性；不降帧、降低分辨率、放宽阈值保候选。

结论状态：研究建议可附条件接受；没有任何跨引擎性能/最低能耗/最终最佳画质放行。剩余真机与prototype为后续工作，未在本轮运行。
