## 原因与复验条件

[注销服务](../../backend/src/services/accountDeletion.js)只重试库内仍标为 deletionPending 的用户。旧快照在 A 注销前制作，其中的 A 是正常用户，还包含当时有效的刷新凭据。部署启动时扫描该库无法获知备份后发生的删除。本次能补删，是因为实验明确知道 A 的 ID。

上线前应把已接受的注销事件写入独立于业务库恢复点、可在灾难恢复时取得的记录，以最少的内部账号标识及顺序定位；明确其保留期、访问权限和可验证的完整性。恢复库先隔离，补放覆盖快照到切换期间的注销事件，核对业务集合、头像和访问结果，完成核对后再开放流量。记录缺失、有空档、补删中断或验证失败时保持隔离。复验至少覆盖跨备份时间点的注销、重复或中断的补删、缺失记录和正常账号对照，再确定发布状态。测试用 ID 补删只验证了清理效果，生产补放机制仍待实施。

### 现有服务器的启用与恢复顺序

1. 在现有服务器收敛写入并停止所有业务 API 实例，核对正在使用的业务库、待处理注销项，以及头像和备份位置。现网使用单文件 server.js，应把启动前核验接入其实际监听入口。11/10 只读核对时该入口仍为旧版本。
2. 在现有副本集内可使用单独命名的注销库，配置 `DELETION_LEDGER_URI`。另设 `DELETION_CHECKPOINT_DIR` 指向受限持久目录，由运行服务的账号可读写，放在业务库和头像还原范围之外。两者须能取得到停写时的最新独立副本；同一主机损坏或两份证明一起回滚，单凭旧业务库无法识别缺失的注销。该跨故障域保护和实际恢复点仍待验。
3. 仅在经核对的当前业务库、新的空注销库上，载入服务环境，运行 `node src/scripts/initDeletionLedger.js --initialize-live-baseline`。初始化不接收历史快照作为基线。安装覆盖停写窗口中所有服务实例，再制作一份新的业务库及头像备份，确认归档内含 `deletion_ledger_anchor`。此前历史备份继续隔离，不能直接切回服务。
4. 恢复时保持原服务停写，目标隔离，使用明确的业务库命名空间还原 MongoDB，并将配对的头像包还原到空目录。提供经核实的最新注销库和检查点。出现缺项时从可信副本核对恢复，保留现场，避免重新初始化或借旧检查点放行。
5. 在隔离环境启动实际服务；核对正常对照账号和注销测试账号的资料、凭据、数据与头像，再切流。若无法证明注销记录覆盖到停写点，保持隔离。启用后，回退代码也须保留注销登记和启动核验。
6. 确认最长可恢复备份窗口、过期清除和异机告警后，再确定注销记录的清理办法及政策文本。当前实现未自动清理事件与检查点。上线前需据实际保留策略告知用户保留的内部标识、用途和期限。
