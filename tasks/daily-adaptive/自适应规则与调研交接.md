## 二 已确认的适配原则与设计理由

![用户指定的iPhone 16 Pro参考原图](../../output/daily-adaptive-semantic-review-20261006/user-reference.png)

此图是用户指定的设计参考，不是最新Figma精调效果，也不是待认可候选的验收图。

### 1 球桌优先但必须完整可操作

球桌是主要工作区，承载球形、线路和落点判断。先保证必要操作、读数、触点及退出路径，再在可行方案中尽可能扩大实际球桌。常驻统计、副标题、重复提示和装饰外壳不应长期挤占桌面。

“桌面尽可能大”不能只看中央 stage 矩形。必须分别记录 window、扣安全区后的 page、stage、实际投影桌外框、台呢内框，并指出当前由宽还是高限制。不能拉伸球桌、裁袋口来提高占比，也不能要求不同宽高比都达到同一个面积百分比。

2D 保持真实比例、完整外框和六袋；**台呢内框 2:1，不意味着含库外框也是 2:1**。3D 场景铺到 HUD 后方，按观察任务评价取景：全局观察应看完整桌面，沿杆机位可以裁近端，不能用 2D 完整桌框标准迫使所有 3D 机位无限后退。

### 2 球库必须单行且能用手指选球

- 母球独立在左；目标球序列围绕球桌/HUD 中线居中，不能把含母球的整排机械居中。
- 中八按 1–7｜8｜9–15 分区；其他玩法按自己的固定集合居中。短球库不必拉满；进袋后保留暗显槽位，避免全排跳动。
- 最新 2D 精调决定：球库下沿贴桌外框上沿，不另加装饰间隙。3D 继续使用稳定的 HUD 锚点，不追着透视袋口漂移；具体同步以已确认布局为准。
- 可见球径、槽宽、槽高、间距与真实命中区分别量测。历史 27/32pt 槽宽不是“所有设备都容易点”的证明，也不能给每球叠加相互重叠的 44pt 热区伪造达标。
- 空间不足先回收无用留白、协调标题和模式组；仍不足才比较单行滚动降级。滚动并非已获准的常态方案，更不能为全显示无限缩球。
- 首末球、分组边界、非法/已进袋球实际点选；点按和滚动/拖球分开验证。模拟器中心点击成功不能代替手指舒适性。

### 3 两侧控件继承成对关系和操作记忆

参考手机的关系是：开球在左上、击球点在右上；方向在左、杆速在右；双尺有效行程等长、上下端点对齐；重打/回放在左下、击球在右下；3D 相机入口位于右侧仪表外侧。

两侧按钮应在**真实剩余空间**内尽可能大，同时保持整齐、美观和主次。不能先加宽侧栏把桌挤小，再声称按钮更易点；也不能所有尺寸永久用最小按钮。击球与辅助动作不必等大，短屏允许重打/回放横排。

左右尺外壳总高度可因标签和杆速读数不同而不同；比较的是有效尺区，不应因此错位。跨 2D/3D 保持共同动作的位置记忆，3D 专属相机功能单独预留，不能只看 2D 暂时空白就删除通道。

### 4 双尺使用实用定长而非随屏幕拉伸

用户明确：16 Pro 的方向/杆速条已经尽可能长；iPad 不需要跟随大屏尺寸拉长，采用合理固定长度即可。既有 **144pt 有效行程**是保留参考，iPad 首个候选也以此为起点；这不是所有未来设计永远不可调整的物理常量。

保持快滑粗调、慢滑精调、连续值、无吸附/无惯性、反向及时响应。刻度、声音和震动不接管数值；停手和松手不产生额外变化。长度如需调整，必须同时验证灵敏度、读数、端点、触感和手指遮挡，不能只判断外形。

### 5 按空间容量选择结构

| 可用空间 | 已确认的判断方法 | 仍需具体设计的部分 |
|---|---|---|
| 参考横屏手机 | 保护 16 Pro 已有构图和控件关系 | 不为参数统一而破坏参考 |
| 短或窄手机 | 先回收空隙，再局部重排辅助动作 | 不用缩字、裁读数或重叠触点换取放得下 |
| Max 或宽平板 | 新增空间优先给桌面，剩余空间改善按钮/球库并合理封顶 | 空白需解释用途，不能强行拉伸真实比例球桌 |
| 近方形窗口 | 比较左右仪表与利用桌上下空余区域的结构 | 桌下操作组仍是候选，未被正式认可 |
| 极小窗口 | 先合理重排，确实低于操作容量才受限呈现 | 必须可返回、可恢复；不能只算 fits=false 后照旧画 |

断点由控件自然尺寸、文字、必要间距、安全区和状态推导；不凭机型名或臆造的宽高比阈值决定。布局可以有离散档位，档位内部使用弹性空间。Figma 某张画板的坐标是设计输入，不自动等于生产代码的机型分支。

## 三 尺寸应该怎样分类

单位除另注外均为逻辑 pt。以下是历史参考，**不是把最新 Figma 精调强制改回旧数值的命令**。

| 类别 | 已有参考或约束 | 使用方式 |
|---|---|---|
| 物理/几何事实 | 球、袋、杆、台面真实比例；2D 内框 2:1 | 消费几何与资产真源，不因屏幕改变物理 |
| 稳定设计关系 | 单行球库、目标序列居中、成对双尺、共同操作位置 | 优先保留关系，具体重排例外需明确确认 |
| 参考手机解 | 顶栏44、侧列60、上入口48、辅助44、击球60 | 解释来源后按容量处理，不能统一固定或统一放大 |
| 球库参考解 | Pro球面30、槽32×44；小屏球面25、槽27×44 | 说明已有密度，手指舒适仍需验证 |
| 定长偏好/封顶 | 尺区144、可见尺宽32；打点整卡264/白盘160；设置参考宽252 | 分别表达行程、上限或参考宽；不能据此裁文字/关闭 |
| 触点保护 | 打点四向键44等 | 独立可点；小屏优先压缩白盘，不同比压缩所有操作键 |
| 弹性空间 | 桌周空白、间距、两翼、相机通道 | 先辨明用途，再回收或增长；球库贴桌关系单独保护 |
| 交互调校 | 防遮挡启动区、轻点阈值、粗细增益、声震限频 | 布局变化后真实操作复验，不按屏幕倍率改值 |

当前 C21 精调中的 Pro 尺宽42、Max/iPad 尺宽44等是待确认设计值，不应与旧“可见尺宽32”的定义混用；更不能把 Figma 图块外框高当成 App 的有效尺区行程。

## 四 其余设计契约不能在适配时丢失

下表覆盖原规范全部 28 项，便于另一会话按改动范围加载原文；它不替代详细交互与业务真源。

| 契约 | 必须保留的含义或边界 |
|---|---|
| DC01 球桌 | 在可操作前提下最大化真实桌面，临时模态不变成常驻压缩 |

| DC04 球库排列 | 目标序列居中、母球独立、固定槽位；最新2D球库紧贴桌沿 |
| DC05 球库状态 | 淡绿底=合法目标，白细圈=当前瞄准球，暗显=已进袋；不混成一个选中态 |
| DC06 球库触点 | 视觉与命中分开，单行易点，不能重叠热区或仅凭AX判舒适 |
| DC07 成对仪表 | 开球/打点、方向/杆速对应，主辅动作有层级；新结构例外另审 |
| DC08 精调尺 | 粗细调连续，尺长合理封顶，刻度反馈不量化实际输入 |
| DC09 显式击球 | 松手只更新预览，点击击球才执行；迟到结果不自动出杆 |
| DC10 打点大盘 | 四键、回中、读数、可达域完整；整卡在未缩放2D内框，双模式同锚；起手避挡、取消清理 |
| DC11 透明度 | 默认50%，越大越透明；只改大盘白底；关闭设置保留大盘，偏好跨模式/重启；浮层空白不透点 |
| DC12 材质反馈 | 轻黑透明底、白细框；击球常态与HUD同色，仅按下淡绿；不染球面/文字 |
| DC13 更多菜单 | 透明度、击球设置、临时玩法、显示；显示组置底，菜单不重复重新开球；末项可达 |
| DC14 辅助显示 | 2D三档，3D另有关闭；关闭辅助不删真实桌面标记/球杆，不更改选择和调参 |
| DC15 瞄准特写 | 硬避让关键球、六袋、线路和完整球杆；无位先缩小再隐藏，不用遮挡最少兜底 |
| DC16 用户意图 | 合法、可直进、当前杆能否进球分开；手选不受自动推荐舒适档限制，刷新不暗换球袋 |
| DC17 点击反馈 | 确认动作不承诺结果；手动袋口立即0.6秒，自动推荐延迟1秒；取消过期反馈 |
| DC18 相机 | 普通调杆速/打点不抢镜；全局就近选四边、重复点击不循环；俯视与自动取景有明确生命周期 |
| DC19 提示决策 | 无操作短提示靠内框上沿、不占行；有操作决策/结果居中，阻断冲突输入 |
| DC20 开球重打回放 | 开球停稳直接交付；主动重开确认保留；重打恢复快照、回放不计新杆，取消旧动画回调 |
| DC21 入口与草稿 | 恢复同盘、默认与临时玩法分开，丢进度需明确确认；本机保存不宣称跨设备同步；不恢复已撤销预加载门控 |
| DC22 连续预览 | 最新完整参数决定可执行杆，旧结果只作有区分的预览；中断清理，不以物理降精度换流畅 |
| DC23 可访问性 | 看真实文字边界与命中；大字号换行/重排/局部滚动；AX完整或hittable不等于视觉完整 |
| DC24 容量适配 | 操作约束→扩大桌面→剩余空间改善控件；常量类别分开，近方形要比较结构 |
| DC25 手势权限 | 观察、选球、摆球分工；临时俯视不是完整2D；母球拖摆由规则允许，目标球不能任意移动 |
| DC26 声音触感 | 反馈有效位移，停手不续响；声震分别限频，听感/手感须真机 |
| DC27 背景 | 2D低对比真实地毯，3D真实房间；背景不参与触摸，扩大区域不拉伸纹理 |
| DC28 同一事实 | 显示、规则和物理一致；布局不改球袋大小、轨迹结果或成绩口径 |

## 五 已做的调研和能够得出的结论

### 1 历史截图与设计记录研究

### 3 原生布局机制与外部资料研究

以下归纳既有v2调研，链接保留作后续查证入口，本轮没有重新验证外部资料版本或API可用性。v2冲突的产品要求已由v3及最新用户决定覆盖。

| 研究结论 | 对本项目的实际意义 | 既有来源 |
|---|---|---|
| 使用逻辑pt，像素与display scale分开 | 不能把PNG尺寸直接当触点，也不能按屏幕像素倍率缩放HUD | [Apple Images](https://developer.apple.com/design/human-interface-guidelines/images) |
| SwiftUI按父级提案、内容量测、放置协作 | 实际容器与内容决定是否放得下；Size Class只作粗判断 | [WWDC自定义布局](https://developer.apple.com/videos/play/wwdc2022/10056/)、[Layout](https://developer.apple.com/documentation/swiftui/layout) |
| 优先内建布局，必要时局部自定义 | Stack/Grid/alignment解决普通布局；AnyLayout用于同元素重排；ViewThatFits候选限轻量HUD，不复制SceneKit场景 | [AnyLayout](https://developer.apple.com/documentation/swiftui/anylayout)及[v2机制表](../DAILY-ADAPTIVE-LAYOUT-PLAN-V2-20261006.md) |
| 安全区由所属容器负责且只扣一次 | 背景可延伸，交互另保护；不能全局屏宽扣固定边距 | [UIKit Safe Area](https://developer.apple.com/documentation/uikit/positioning-content-relative-to-the-safe-area) |
| 字号与窗口缩放是不同问题 | ScaledMetric响应Dynamic Type；大字号用内容重排，不能整页scale抵消需求 | [ScaledMetric](https://developer.apple.com/documentation/swiftui/scaledmetric) |
| iPad必须验证变化过程与恢复 | 固定全屏图或受控容器不能替代真实系统窗口测试 | [iPad窗口设计](https://developer.apple.com/videos/play/wwdc2025/208/)、[UIKit窗口适配](https://developer.apple.com/videos/play/wwdc2025/282/) |
| 可访问性审计是辅助证据 | audit无失败不代表文字、边缘触点、手指遮挡和VoiceOver全通过 | [Accessibility Audits](https://developer.apple.com/documentation/accessibility/performing-accessibility-audits-for-your-app) |

### 4 最新标准化分析发现

C23读取本地Figma两文件，五屏粗调与交接快照几何指纹一致；本轮仅分析，没有修改布局。以下是最新记录的具体问题，不是本摘要新跑的测量：

- **水平锚点**：16 Pro粗调彩球条中心与桌中心约差−0.5pt；C21整体球库居中后，iPad竖/横彩球条分别偏右约25.29/27.97pt。C22只修纵向贴边，水平仍待修。
- **桌面积**：Pro桌宽627→612、Max711→680、竖Pad595→582.1，缺少已确认的容量或安全区理由；不能仅为整齐留边缩桌。
- **真实尺区**：原Pro方向外框44×174、杆速44×190，内部都是32×144；外框高差来自读数。C21按宽42整体缩放后尺区约30.55×137.45，文字约9.55，不能声称仍保持原有效行程。
- **内部结构**：SE开球外框50而内部圆盘42.86，击球点盘48；有些48辅助按钮内部仍44且不居中。仅把外框调成相同尺寸不足以标准化。
- **净空与文字**：iPad横屏击球边缘恰贴桌边，矩形重叠为0仍显拥挤；不同屏文字被粗缩放成约8.18/9.55/10等，应独立规范字号。
- **功能集合**：SE粗调缺回放不代表用户批准删除。标准化需核对完整操作及容量。

C23建议下一轮以16 Pro粗调为主参考，依次处理组件内部、关系锚点、间距/尺寸档、五屏对照。4pt基本调整单位、4/8pt组间候选、44/48辅助按钮、48/56顶圆盘、50/60主按钮，以及小屏必要时缩短轨道，均是**尚未实施的建议**，不是已确认的全设备常量。缩尺仍须满足前述容量解释和交互复验，不能反过来削弱16 Pro基准。

## 七 实施与验收如何衔接

用户确认设计后，再以实际范围接回v3批次：R1空间结构、R2顶栏/球库、R3浮层/大字号、R4窗口/生命周期、R5综合与真机体验。当前不要直接启动；旧R1取舍未闭合，R2–R5没有被Figma草稿替代。

每项改动按“DC条款 → 现状问题 → 保留关系 → 收益/代价 → 对应证据”登记。技术落点优先沿用FreePlayView的每日HUD、DailyLayoutMetrics、ShotTableLayout/CameraRig和AngleSceneView/LayoutAwareSceneView；开工时核查实际拥有者及调用方，不据历史行号直接编辑。布局不重建ViewModel/renderer，不改变物理或计分。

每轮证据至少区分：

- **静态设计**：Figma对齐、比例、紧凑关系、可见内容；结构变化需可比较方案。
- **原生视觉与交互**：同条件before/after、真实触点/滑条/菜单末项、关闭与底层拦截。
- **几何与生命周期**：逻辑pt/屏幕frame分开，投影与命中一致；真实窗口变化、后台、模式、重开和取消旧手势。
- **真机体验**：手指点选、握持、遮挡、连续调节、声音触感、温升性能。
- **用户认可与交付动作**：认可的设备/状态单独记；安装、提交、发布分别记，不自动外推。

R1历史candidate3构建、14项度量单测、6项定向UI通过且采集60图，只能按[报告](../ui-reviews/UR-20261006-daily-r1-space.md)范围复用。球库舒适、完整浮层最大字号、真实iPad窗口恢复、全域3D/HUD遮挡和真机声震热量仍有缺口；FL-124稳定性与FL-094遮挡按各自专项证据核实，不因此次汇总自动关闭。
