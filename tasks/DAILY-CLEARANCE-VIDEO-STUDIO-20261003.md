# 每日一清台录制台：第一版方案

日期：2026-10-03；版本：v1.0；状态：详细方案整理，实施暂缓，等待每日清台功能完成。

用户最新范围：**先定详细方案，后面等每日清台功能做完再说。** 本文中的实现顺序是未来计划，不是本轮执行授权；不启动功能编码、构建、安装、录局或出片。

## 1. 用户目标与范围

用户在模拟器中亲自完成一局每日清台，从开球前开始保留所有序列数据到指定文件夹；之后使用 App 引擎逐帧渲染视频，支持事后编排镜头。

用户已确认上一轮理解：独立制作入口复用每日清台的操作与规则；球局数据与镜头方案分开保存，同一局可反复出片。本轮只完善详细方案。

第一版建议仅模拟器制作入口可见，支持同一天多局与跨日续录。制作局有独立存储空间，不写入正式每日挑战的草稿、完成记录或训练统计。上述隔离是实现建议，非现有能力。

## 2. 已核查的基础与缺口

| 来源 | 当前源码能力 | 新录制台需要补齐 |
|---|---|---|
| `PositionPlayViewModel.startRecording/appendRecordedStep` | 普通击球记录前后盘面、意图、进袋集合 | 实际执行方向、完整回放记录、旋转姿态、规则变化；不再只依赖事后反解 |
| `PositionPlayViewModel.replayCurrent` | 录制时撤回末杆 | 原始尝试保留，最终采用路线单独引用 |
| `PositionPlaySequenceArchive` | 模拟器直接写 Mac 的内容库 | 独立输出目录、逐杆保存、恢复与失败诊断；不套用同 ID 清理旧文件的规则 |
| `BreakFlowRunner/BreakSimulator` | 独立开球输入、运动记录、停稳交付 | 从开球前捕获；不能只监听普通击球回调；区分物理停位与白球补回 |
| `DailyClearanceController/Store` | 规则裁决、轻量草稿、完成、单杆重打 | 独立制作会话；正式草稿跨日清理规则不可用于长时间制作项目 |
| `TrajectoryRecorder/TrajectoryPlayback` | 物理帧、事件关联记录、空间段与派生进袋收尾 | 可持久化的值类型快照、解码后回放适配与版本契约；当前不是完整 Codable 存档 |
| `SequenceVideoExporter` | SceneKit 逐帧编码、杆号/参数、部分瞄准/观察转场 | 消费已录制运动与规则事件；现有逐杆重新模拟、重新摆 before 的路径不能直接作为实战精确复现 |

现有二维 `BoardSnapshot`、`SequenceStep` 与内容生产契约继续保持。制作局包是新类型；不得把开球、多次尝试或三维轨迹塞进官方 Drill 内容库。正式实现跨模块边界时再按项目规则追加 ADR。

## 3. 操作流程

1. 打开“每日一清台录制台”，新建制作局；选择现有玩法，记录实际球架与 seed。
2. 从开球准备开始自动记录；用户自行调整母球、方向、力度和打点并开球。
3. 按每日清台规则继续击球；逐杆显示“保存中 / 已保存 / 保存失败”。
4. 重打保留旧尝试并建立新分支；重开建立新球架段，保留旧段。退出后可从已提交停稳状态继续。
5. 清台、规则判负或手动结束都可归档，状态明确区分。只在生产规则确认完成时标记“清台成功”。
6. 选择已保存球局与镜头方案，先预览，再逐帧导出到该局的 renders 子目录。

录制工作期间只记录真正提交的操作和已经执行的运动。预览预测、上一杆回放、切换 2D/3D 不增加击球次数或产生重复杆。

## 4. 文件包与数据合同（拟定）

默认目录建议为 `output/daily-clearance-recordings/`，实际指定目录尚待用户提供；通过制作配置统一传入，不散落到多个硬编码路径。每局以日期与完整 UUID 标识，重命名不改稳定身份。

```text
<root>/<date>_<session-uuid>/
  manifest.json                 # 版本、玩法、状态、文件清单与哈希
  session.json                  # 初始盘面、规则、当前分支、恢复检查点
  actions/<action-uuid>.json     # 开球/击球/重打/摆球/规则选择/重开等操作
  shots/<shot-uuid>.json         # 实际输入、运动、事件、前后状态
  camera/<plan-uuid>.json        # 镜头、节奏、信息层与时间映射
  renders/<render-uuid>/         # 新输出，不覆盖旧片
    video.mp4
    render-manifest.json
    verification.json
```

数据字段按以下职责设计，具体 Swift DTO 在 W0 验证后冻结：

- **会话**：schemaVersion、完整 sessionID、玩法/规则版本、创建/更新时间、状态、球架段、活动分支、恢复检查点、录制完整性。
- **球架**：实际 seed、实际初始盘面与球身份；保存真实球位，不依赖未来用 seed 重新生成得到相同架。
- **击球输入**：开球/普通杆类型、用户意图、实际解算后执行方向、实际杆速与打点、物理模型/参数快照。不能只存目标球/袋口后在导出时重新求解。
- **运动**：稳定球键与预测别名映射；物理时间、位置、速度、自旋、运动状态；当前模型实际使用的空间段、捕获、进袋收尾及声音事实。缺少必要字段应拒绝“完整录制”标记。
- **呈现起止态**：球旋转姿态、在桌/离桌身份、网兜/支架库存与派生尾段所需状态，避免换杆后贴纸方向重置或已进袋球复活。
- **规则**：原始 ShotFacts、裁决、规则前后状态；分别保存物理停位和裁决/补球/摆放后的可继续盘面。补回或移动必须有显式操作，不能伪装成连续球运动。
- **来源**：App/build、源码版本与本地改动摘要、物理/回放契约版本、几何与渲染资源标识及哈希。资源不匹配须提示，禁止悄悄重新模拟替换旧运动。

旧二维盘面沿用已有归一化坐标合同；三维记录沿用生产回放的场景坐标与计量单位，并在包内写明转换合同。实施涉及几何转换前须读取几何技能与桌面真源，不在方案中另造尺寸。

动作以唯一 ID、单调 revision、前置 checkpoint 与引用文件关联。原始动作和运动文件写入后不被重打删除；活动分支决定成片采用哪条路线。无重打的失误或犯规也是实际路线的一部分，不能为了“成功视频”直接删掉并拼接不相接盘面。

## 5. 保存、退出与恢复

实际执行输入通过合法性检查后，先持久化待执行操作。模拟完整且准备播放时保存运动快照；播放结束、规则结算和派生支架收尾完成后，提交可继续检查点。各阶段均校验会话/杆代次，取消和重开不能兑现旧回调。

编码和批量文件 IO 在持久化服务中串行执行；从运行时对象获取值快照时遵守其线程约束，不把可变 recorder 或 SCNNode 跨线程当成不可变数据。需要在播放后补充的派生尾段由独立版本提交，不修改已发布运动事实。

先写临时文件并原子替换单个文件，关联数据成功后再发布引用它们的 manifest；不能把多文件写入误称为单一原子事务。恢复时验证版本、引用、长度与哈希，检查点只引用已经完整提交的动作。残留临时文件和悬空操作保留诊断，恢复上一个有效检查点；不得补造运动或重复结算。

保存失败需明确报错并允许重试；重试沿用同一动作 ID，成功前不显示“已保存”，不静默继续一个无法保证完整性的新杆。退出不删除文件；跨日不过期。第一版只承诺已提交停稳点的续录，运动途中恢复的呈现策略必须实测后再承诺。

## 6. 第一版镜头与时间轴

镜头不改球局数据，也不运行新的击球求解。编辑后可对同一录制包生成多个视频。交互镜头仅作为可选参考，视频镜头按自身画幅和观看目的编排。

| 预设 | 流程 | 适用 |
|---|---|---|
| 固定全桌 | 开球/每杆保持同一全桌观察机位 | 首轮对拍与完整路线基线 |
| 瞄准后切观察 | 开球全桌 → 停稳 → 本杆读盘/瞄准 → 击球 → 进袋或杆末切观察 → 下一杆 | 每日清台成片默认候选 |

进袋触发必须来自本杆实际规则事件；所选目标未进时在杆末回观察。开球没有单一目标球，单独使用全桌规则。记录物理停稳和派生进袋呈现结束两个时刻，不能在尾段未结束时重置画面。

真实操作耗时与视频时间分开：思考/调参数时间默认压缩为可配置读盘和瞄准停顿，球运动默认原速；不锁死总片长。倍速时镜头、声音、杆号、事件触发共用同一时间映射。相机位置/朝向/FOV/显隐按绝对输出时间求值，支持乱序取样与重复渲染。

首版支持自动预设及每杆覆盖：视角、停顿、切换触发点、硬切/平滑转场、轨迹和打点/力度/杆号显隐。复杂跟球、多视角小窗、旁白配乐与封面不作为首个闭环前置。

平滑转场需检查真实球桌/房间实体与关键对象可见性；数值连续不等于穿桌安全或画面好看。当前每日清台相机候选仍在返修，不能把候选局部测试直接当作视频镜头验收。

## 7. 实施顺序与验收

| 批次 | 交付 | 核心验收 |
|---|---|---|
| W0 录制合同探针 | 实际开球及普通杆的值快照序列化/解码/回放适配 | 运动、事件、捕获尾段、初始旋转和稳定球键往返一致；在导出消费端观察真实节点，不只看文件可读 |
| W1 持久化 | 独立会话包、逐杆提交、保存失败与恢复 | 逐提交点故障恢复、不重复结算、损坏报错、重试幂等、跨日续录、重打保留尝试 |
| W2 制作入口 | 复用每日操作/规则的模拟器入口 | 从真实手动开球开始，多杆、自由球、重打、重开、退出续录；正式每日草稿/完成和统计保持隔离 |
| W3 固定镜头导出 | 已录制运动直接驱动生产 SceneKit 场景与编码 | 从开球至后续杆对拍；不调用新的求解替换运动；前后盘面只允许通过记录操作衔接 |
| W4 镜头编排 | 两预设、逐杆覆盖、事件/时间映射 | 无目标进袋、多个进袋、大角度跨台和尾段边界；不同镜头输出运动与规则不变 |
| W5 整局验收 | 用户亲自完成的整局包、成片、验证报告 | 球数/身份/停位/规则终局；重开与取消不串局；编码后抽帧和连续片段目视 |

不生成 AI 球形或代用户自动清台来替代整局录制验收。可用用户已有真实录制资产作兼容样本，最终整局须来自新入口的真实操作。

正式成片沿用高码率原生逐帧母版要求；具体画幅、像素尺寸、fps与声音方案仍待本片需求确定。用 ffprobe 验实际尺寸、帧率、时长、码率和音轨，并检查编码后视频。离线导出速度不作为 App 实时性能证明。

## 9. 等待条件与第一版边界

实施启动前，用户确认每日清台功能已完成并可作为制作基础；届时重新核对实际源码、未提交变更与相关规则契约。当前普通杆、开球、规则结算、重打、退出恢复、镜头控制的接口只是调查时点的实现，不能把本方案永久绑定在这些私有细节上。

制作台不复制另一套每日规则或物理求解器。复用成熟的交互、规则与场景；新建的是制作会话、数据采集、文件持久化和导演时间轴。若届时控制器无法注入独立存储，先在未来 W0 列出最小边界改造并补 ADR，不靠临时改 UserDefaults 全局 key 或替换正式草稿实现隔离。

| 第一版包含 | 后续可扩展 |
|---|---|
| 模拟器制作入口、新建/续录/归档/局列表 | 真机录制与跨设备同步 |
| 从手动开球开始，复用届时每日支持的玩法 | 自定义赛事规则、额外球架或 AI 自动打球 |
| 原始尝试全部保存，活动分支单独选择 | 任意历史节点的复杂树形编辑器 |
| 保存失败重试、停稳点恢复 | 击球动画中途无缝接着录制 |
| 固定全桌与瞄准/观察两种预设、每杆覆盖 | 实时录制手指镜头、跟球、袋口小窗、多机位同时出片 |
| 视频预览、无声/原生击球音效配置、高码率母版 | 自动旁白、配乐、封面、平台发布 |

首版沿用届时每日清台全部支持玩法。当前源码为中八、9 球、6 球、5 球、4 球；自动验收先用真实较短球局走完闭环，再覆盖用户主用玩法。该验证顺序不限制用户录制内容。

## 10. 页面与操作合同

制作入口建议挂在现有模拟器专用制作工具区域，命名“每日一清台录制台”。最终入口位置待每日清台界面定稿后适配。

| 页面/阶段 | 可执行操作 | 必须显示的信息 |
|---|---|---|
| 局列表 | 新建、继续录制、查看、进入出片 | 日期、局名、玩法、状态、当前路线杆数、最后保存时间 |
| 新建 | 命名、选择玩法、开始；高级设置中修改保存根目录 | 实际保存路径；新局不继承旧局已打出的盘面 |
| 录制 | 每日原有瞄准/力度/打点/选球袋/击球与合法摆球 | 小型录制标记、当前局名、保存状态；不覆盖现有关键操作 |
| 开球待确认/规则选择 | 沿用每日原有选择 | 当前结果与规则选择；不能偷偷筛选球架或自动重开 |
| 停稳 | 重打、重开、退出保存、手动结束 | 当前路线与原始尝试数量；保存失败时明确指出未保存操作 |
| 完成/判负/手动结束 | 查看回放、进入出片、新建下一局 | 真实完成类型、杆数/犯规/上手等可确认统计；状态不能都叫清台成功 |
| 出片配置 | 选择球架段/分支、预设、规格、信息层、声音 | 预计时长、采用杆数、是否含开球、输出位置 |
| 单杆镜头编辑 | 预览阶段、改视角/停顿/切换方式、恢复预设 | 当前杆真实参数、事件标记和运动时间；编辑不重算运动 |
| 导出结果 | 播放、查看文件、按新配置再导出 | 原片路径、实际测量规格、配置版本、验证状态 |

第一版不提供随意删杆后自动拼接盘面的按钮。选择另一条历史尝试必须建立从初始球架到终局的有效路线。手动结束后的恢复仅对仍可继续的球局开放；已被规则判负/完成的终局不绕过规则继续击球。

## 11. 会话与动作状态机

会话业务状态与保存状态分开。`saving` 不是一局玩法阶段，`saveFailed` 也不等同规则判负。

| 会话状态（拟定） | 进入条件 | 后续 |
|---|---|---|
| prepared | 新局初始球架和规则提交完成 | 手动开球 |
| recording | 一局尚未终结，可处理规则操作 | 正常击球、合法摆球、重打、重开 |
| suspended | 已保存当前停稳检查点后退出 | 从同一检查点续录 |
| completed | 生产规则返回 completed | 归档与出片 |
| failed | 生产规则返回 failed | 归档与出片，或按原规则重开新段 |
| ended | 用户主动结束非终局制作 | 查看/出片；满足规则条件时恢复 |

运行时另有 computing/playing/settling 等每日既有阶段，直接复用。制作台只在停稳且保存成功后提供安全的重打/退出边界；强制退出后的恢复按第 5 节处理。

每个击球尝试的记录状态拟定为：`intentSaved → motionSaved → playbackFinished → rulingSaved → committed`。另可终止为 `rejected/cancelled/interrupted`。记录完整模拟结果不等于用户已经观看/打完本杆；不能仅因 motionSaved 就发布下一杆检查点。

非击球动作最少包括：`rackCreated`、`breakAccepted`、`breakChoiceResolved`、`cuePlaced`、`ballRespotted`、`undoApplied`、`rerackRequested`、`sessionSuspended`、`sessionEnded`。正式类型名在实现时冻结，语义保持可审计；规则派生操作和用户手动操作分别标明来源，幂等动作不得重复改变状态。

重打示例：初始架 → 开球 B → 普通杆 A1 → 普通杆 A2 → 撤回 A2 → 替代杆 A2b。原始动作保留 A2 和撤回事实；最终路线为 B/A1/A2b，并校验 A2b.before 对应 A1 之后的规则/合法摆放结果。

换一局示例：球架 R1 已打若干杆 → 重开 → 球架 R2。R1 与 R2 共属同一制作项目但不同球架段；默认出片选择一个完整段，不把 R1 的开球接到 R2 的清台。若以后做合集，段与段之间明确标示新局。

## 12. 数据细化与版本约束

| 文件 | 必要字段（拟定逻辑名） |
|---|---|
| manifest | schemaVersion、sessionID、revision、status、createdAt/updatedAt、相对路径/hash/长度、当前 session 文件引用、previousRevision |
| session | name、game、ruleVersion、rackSegments、activeBranchID、checkpointID、actionHeads、sourceProfileID |
| action | actionID、revision、type、source、前后 checkpoint 引用、shotID/segmentID、记录日期、业务载荷、执行状态 |
| shot | shotID、kind、beforeCheckpointID、resolvedInput、simulationTermination、motionRef、presentationRef、facts、rulingRef、afterCheckpointID |
| checkpoint | board、球姿态与身份、规则状态、支架/网兜呈现状态、所属 segment/branch、可继续阶段、已计数动作集合 |
| camera plan | planID、version、sessionRevision、branchID、defaults、shotOverrides、outputProfile、audioProfile、timelineMapping |
| render manifest | renderID、录制包 revision/hash、镜头方案 hash、资源版本、实际输出规格、帧数/时间范围、验证文件引用 |

实现可把 motion/presentation 拆为独立每杆数据文件以减少载入与重写；目录示例不要求把大段轨迹全嵌入 session.json。检查点放置方式也以 W0 的大小/载入测量确定。

**时间与身份合同**：

- 日期仅用于检索与命名；动作先后由 revision 和前置引用决定，不能按系统时间排序，避免改时钟/跨日破坏顺序。
- 每杆运动时间相对该杆触球起点；全片时间由导演时间轴映射。空间原记录的 Double 时间与平面原记录的 Float 时间保留来源精度，把 Float 转为 Double 不宣称精度提高。
- 帧时间允许生产记录中的同刻碰前/碰后状态；用记录序号/阶段保持顺序，不能简单按时间去重或要求全部严格递增。事件同样保留稳定原始顺序。
- 球键使用稳定业务身份；普通杆内的 `object` 等预测别名仅通过该杆映射解释，跨杆不得当作同一实体。袋 ID、库索引、几何索引都带所属版本域。
- 物理捕获时间决定规则事实，网兜下落与支架动画是呈现记录。两者不能互相替代；未进球不因画面剪切或后快照而变成进球。
- 必要数值必须有限；解码失败、未知主要 schema、未知且影响规则/运动的动作类型明确拒绝完整回放。可选的纯展示扩展可以忽略，但需留下诊断。

**资源与兼容合同**：保存资源标识和哈希支持检查一致性，不等于资源母版已经被归档。第一版重放依赖匹配的 App/回放合同与资源；若资源变化，提供明确不兼容结果，不能承诺任意未来版本像素完全相同。长期资源母版随包冻结与旧版本转换器另行设计。

“重放旧运动”与“在新版每日功能中继续打下一杆”是两种能力。版本变化时前者可能可用、后者不一定可用；规则/物理续录兼容不明时允许查看已录部分，禁止静默切换新规则继续原局。

## 13. 导演时间轴与逐杆镜头

| 阶段 | 球局时间 | 画面建议 | 信息层 |
|---|---|---|---|
| 开场 | 初始停稳点冻结 | 全桌、实际球架与玩法 | 局名/玩法，可关闭 |
| 开球准备 | 开球 before 冻结 | 全桌能看清母球与球堆，短暂展示开球方向 | 开球参数，可关闭 |
| 开球运动 | 原记录时间从 0 推进 | 全桌保持，所有运动球有观察空间 | “开球”，默认不画运动轨迹 |
| 开球收尾 | 原记录推进至呈现结束 | 保留进袋尾段，展示散局 | 必要规则结果 |
| 规则处理 | 显式非击球动作 | 全桌展示自由球/补球/选择造成的变化 | 简短动作说明；不展示操作按钮 |
| 本杆读盘 | 本杆 before 冻结 | 观察机位，读局面 | 杆号，默认无参数 |
| 本杆瞄准 | 本杆 before 冻结 | 沿实际执行方向的瞄准机位 | 球杆；轨迹、力度、打点按配置 |
| 出杆/运动 | 原记录推进 | 与瞄准机位衔接；按实际事件回观察 | 移除预测线；参数是否保留可配置 |
| 停稳/尾段 | 推进至实际呈现结束 | 看母球停位、进袋结果与剩余球 | 杆号/结果，轻量 |
| 换杆 | 停稳点冻结 | 转向下一杆机位，再进入下一杆读盘/瞄准 | 切换下一杆参数 |
| 终局 | 终局 checkpoint 冻结 | 全桌终局 | 真实完成类型与统计 |

开球单独标记为“开球”；普通杆显示“第 1/N 杆”起。视频运动段序号另存，不把显示号冒充每日统计杆数。实际统计直接来自该分支的规则数据，并注明是否经过重打；不能把重打后的视频包装为未经重打的一次开球清台。

事件触发候选：有指定目标且实际进袋时使用该球的确认进袋事件；无指定目标或未进袋时使用运动结束。多球同进仍按稳定事件顺序记录，不用数组偶然遍历顺序切镜。导演可逐杆覆盖触发事件，但不得选择本杆不存在的事件。

机位不可用时：预览指出具体杆与原因，提供固定全桌候选；只有明确配置了该回退时才执行并写入 render manifest。无法保证全桌候选有效则停止导出，不能生成空帧或突然补摆终局。近景被库体遮挡的情况优先改镜头，不改球位、球径、库体或物理。

**节奏默认候选**：开场 1.5 秒、开球准备 1 秒、本杆读盘 0.8 秒、瞄准 1.2 秒、杆末停位 0.6 秒、终局 2 秒；均可调整，未作为用户裁定。平滑转场时长根据角度/距离和实际画面确定，不将每次跨台都硬设同一秒数。

第 i 杆在全片运动起点为 V_i，播放倍率为 s_i，运动局部时间 t 对应全片时间 `V_i + t / s_i`。静止观察/瞄准/换杆另占时间；原记录的尾段也采用同一映射。输出第 n 帧采样时刻为 `n / fps`，最后一帧与片段边界通过统一整数帧分配处理，避免逐段独立取整积累漏帧或重复触球。

预览拖到任意时间，应先还原该段所需 checkpoint、姿态和支架状态，再查询录制运动与镜头；不能要求从第一帧顺序播放才能得到正确结果。是否缓存逐球旋转积分由 W0 测量决定，帧率变化不得改变球实际路线。

## 14. 画面、声音与导出建议

初始候选为竖版 9:16、1440×2560、60fps、高码率 H.264；横版可复用同一录制包后续出片。该规格尚未确认，预览检查球径、全桌占比和近景后才能冻结；画幅与 fps 属于镜头方案/输出规格，不影响原运动数据。

新制 3D 视频外观默认沿用已固化的炭黑木纹球桌、绿色台呢、墨龙球杆与生产球房/灯光。录制包记录当时场景资源，视频方案可明确选择录制外观或当前视频默认；若更换外观，保留实际几何与运动，并在配置中写清楚。制作页的操作控件不进入成片，教学信息层按配置输出。

声音提供“无声”和“原生击球音效”两项候选。击球、球碰球、吃库、进袋音效由录制事实生成，不能凭视频帧位置重新猜碰撞。每个声音事件随同一视频时间映射落位，增益规则与音频资源版本写入配置。交互 App 的静音偏好不应导致录像数据中声音事实被丢弃。缺少声音事实/资源时明确报错或选择无声，不默认替用户混入旁白配乐。

导出先验证包完整、路线相接、资源可用和镜头可生成，再检查代表静帧及关键连续片段。最终编码完成后测量文件；取消/失败产物标为 incomplete，不计正式成片，也不覆盖既有成功版本。视频、镜头账本和 render manifest 发布成功后，局列表才显示对应完整版本。

每帧预算与内存参考现有 exporter 的单帧释放策略；录制文件分杆载入，避免长片把所有位图留在内存。W0 实测一杆/开球的包大小和吞吐，W3 实测长片峰值内存，再制定警戒值；不先凭空承诺最大局数、4K 实时或固定渲染时长。

## 15. 验收矩阵与放行标准

| ID | 场景 | 必须证明 |
|---|---|---|
| D01 | 手动开球、原位和移动母球、不同打点 | 起始球架/母球和实际开球输入均保存；开球运动完整 |
| D02 | 普通进球、未进、多个球进袋 | 保存原执行方向/轨迹/事实；不会因重算变成另一结果 |
| D03 | 母球落袋、自由球、终局球重置与开球规则选择 | 物理落袋和后续合法补回分别记录；规则/盘面相接 |
| D04 | 一次/连续重打、取消播放、重开、换玩法 | 旧尝试可查，活动路线正确；代次隔离，无旧回调污染 |
| D05 | 每个保存阶段强制退出、写入失败、磁盘空间不足 | 最后完整 checkpoint 可恢复；失败可定位，不重复杆或结算 |
| D06 | 文件损坏、缺引用、schema/资源变化、跨日 | 明确兼容/不兼容状态；不清空原局或伪造数据 |
| D07 | 连续多杆贴纸/网兜/支架 | 旋转连续、进袋球不复活、库存收尾和恢复一致 |
| D08 | 固定全桌导出与实际录制回放 | 对拍实际节点身份/姿态/事件时间/停位，误差预算依据源精度冻结 |
| D09 | 换镜头、改变 fps/倍速、乱序 seek | 同一运动/规则结果；镜头与声音采用一致时间映射 |
| D10 | 近库、跨台大转角、多进袋、无目标杆 | 无穿桌黑帧；主体可读，触发点真实，回退可审计 |
| D11 | 新建/完成/退出制作局与正式每日往返 | 正式草稿、完成记录、统计不被制作局污染 |
| D12 | 实际整局成片 | 编码完整、实际规格/音轨核验；抽帧与连续片段目视，来源局可追溯 |

自动化断言与视觉审查分列。包完整、运动对拍、规则结果、镜头可读、声音同步、整局实际使用分别给出状态；不能用 build 成功代替以上任何一项。

未来首次放行需要 W0–W5 的实际证据及用户录制的至少一局完整有效路线；未通过项不得在界面标记为正式完成。当前这些检查全部未执行，方案阶段不新增测试或宣称通过。

## 16. 后续恢复工作时的交接

1. 确认每日清台已经按用户要求完成，读取其最新实现和验收记录。
2. 核对本文与当时接口差异，明确是否需要 ADR/最小边界调整。
3. 落定保存根目录、优先成片玩法、重打呈现偏好和输出规格。
4. 从 W0 的真实开球/普通杆往返探针开始，按 W1–W5 顺序推进；不跳过固定镜头对拍直接做复杂镜头。

本方案当前仅供讨论与后续交接；用户本轮“先定方案”的范围优先于其中未来实施计划。

文件组织建议：界面与会话协调放 `Features/DailyClearanceVideoStudio/`；回放/媒体桥接按现有 `Core/Physics`、`Core/Media` 职责接入；文件仓库按现有 Data 层规范放置。最终命名和最小公开接口待基础每日功能完成后的架构预飞确定，不提前大量搬移其现有文件。
