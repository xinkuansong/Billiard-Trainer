# 渲染代码优化方案：保持画面与物理行为（2026-10-01）

状态：S0 进行中，已完成模拟器 CPU 基准与定向回归；分配/真机 CPU/GPU 仍待实证。用户已授权开始，S1 尚未选定热点。执行记录见 [S0报告](RENDER-CODE-OPTIMIZATION-S0-20261001.md)。

## 1. 目标与基线

目标是整理现有渲染代码，使编译器更容易优化，并减少运行时重复工作。在相同画质、分辨率、帧率请求和业务输入下，降低渲染侧 CPU 执行、对象分配与提交开销；GPU 只尝试保持原公式与采样的计算复用。

基线提交：`0e465e0b90d430ba5831368e938e4a4a40b19ac8`，分支 `main`，已推送 `origin/main`。

本次基线保存 71 个文件，包含已有应用代码、球桌资源、测试和任务记录。它保留此前其他任务授权的物理修复；后续本方案以这一版本为固定起点，**不再修改物理引擎**。`tmp/`、忽略的 `build/` 和 `output/` 留在本地。

提交前普通 Debug build 返回 `BUILD SUCCEEDED`，`verify-gate`、`verify-doc-size`、`git diff --check` 通过；本轮未重新执行完整单元/UI矩阵，也未完成真机体验验收。证据：`build/render-code-plan-20261001/`。当前相机 FL-094 与其他任务记录中的待验问题仍按原状态保留，基线提交不代表这些问题已解决。

## 2. 固定边界

| 保持的内容 | 实施约束 |
|---|---|
| 物理、开球、预测与规则 | `Core/Physics`、`Core/Rack`、`Core/PositionPlay` 的生产源码不改；不调摩擦、事件预算、步长、停止阈值、球间距与随机策略 |
| 当前外观 | 球桌 USDZ、纹理、台呢颜色、灯位/亮度、曝光、球材质、反射及阴影效果保持 |
| 当前渲染精度 | 分辨率、MSAA、阴影图规格、灯光积分采样、球影采样与目标帧率保持 |
| 相机与交互 | 视角、FOV、投影、相机所有权、手势反馈、全局重开、进袋回切和动画时间保持；只允许减少已经证明冗余的相同值写入 |
| 渲染架构 | 继续使用 SceneKit；不迁移 Metal 引擎、不换 BRDF、不增加第三方依赖 |
| 编译设置 | 使用已有 `-O` 比较；不通过改为更激进的浮点设置制造收益，不改变 DEBUG/可测试性契约 |

允许触及的生产区域先限定为 `Core/Scene` 的渲染循环、参数组织与着色器生成代码。测试、诊断脚本、写入登记和方案记录可配套修改。若候选需要跨入业务层或变更上述不变量，应退出这一候选，而不是顺便扩大范围。

## 3. 已有优化与证据边界

以下是本轮读取当前源码确认的事实，不能作为待实施的新成果：

- `project.yml` 与 Xcode 工程的默认 Debug 已为 `-O`。此次不会重复宣称打开优化编译的收益。
- `AngleSceneView` 已有显式静态状态下的事件唤醒与停绘。目标继续是静止时无持续回调/重绘；不能以低频轮询替代。未提供动画状态的调用方是否仍活动，需要逐页核对。
- `MobileContactOcclusion` 位于 `MobileTableRendering.swift`，初始化时已按球标识排序；动画应用后读取 presentation 节点，比较已有 SIMD 值，变化后用不可变 Data 合并提交，未变化不提交。不可重新实现这套机制再记作收益。
- 每日清台 `configureDailyClearanceRendering()` 已启用 `.reflection`，并启用减少冗余相机写入的路径。
- `mergesDailyClothSupport` / `factorsDailyClothBRDF` 仍是显式 DEBUG 实验开关，默认关闭。本方案不会直接将它们打开。历史合并 support 实验曾有 iOS 17 图像不一致、无稳定收益，应保留失败约束。
- `DiagramLabelOverlay.update` 已有 geometryKey 比较，但构造键之前仍会读取相机、筛球并排序/组织球位。它只在使用自适应图解标签的页面工作，不能据此推断每日清台的大头开销。
- 灯光 shader 字符串中的采样循环在 GPU 上执行。Swift 的 `-O` 主要影响 CPU 代码，不能把 shader 性能变化归因于 Swift 编译设置。

历史报告 `DAILY-CLEARANCE-RENDER-FOLLOWUP-20260921.md`、`DAILY-CLEARANCE-RENDER-ABLATION-20260921.md` 可用于提出热点假设，不能替代当前版本测量。尤其要区分局部 setter 数量、CPU 方法耗时、GPU 命令执行、完整帧时间和整机温升。

## 4. 候选改动的优先级

| 优先级 | 入口 / 假设 | 具体候选 | 先排除的风险 |
|---|---|---|---|
| P1 | `AngleSceneView.renderUpdate` 的重复状态读取与写入 | 在同一次回调内复用 viewport/相机模式/动画状态等稳定值；确认实际冗余后减少重复设置 | 不能跨回调缓存 presentation；不能漏掉 resize、手势、相机平滑和动画唤醒 |
| P1 | `MobileContactOcclusion.update` 的参数准备 | 分离固定布局与变化数据；测量 Swift 数组、Data、桥接与 KVC 的实际成本，再优化确实存在的多余准备 | `var values = previous` 不必然发生堆复制，需分配证据；Data 的不可变快照不能改成可覆写的 GPU 在途共享内存 |
| P2 | 标签页的 geometryKey 准备 | 稳定球顺序/身份可在拓扑变化时准备；减少每帧 sorted/flatMap 和临时指纹数组，保留逐帧变化判定 | 球增删、换杆、隐藏、投影与表面高度全部进入失效条件；不能以过大的容差忽略变化 |
| P2 | 渲染计算函数中的对象与动态调用 | 经采样确认后，将纯数值计算与 SceneKit 访问分开；使用具体数值类型、短生命周期值与明确循环 | 不泛化重构所有代码；值类型也可能复制，不盲加 `@inline(__always)`、unsafe 或指针 |
| P3 | `MobileReferenceLighting` 中重复 shader 运算 | 仅将确实相同输入、相同精度的子表达式复用；逐个验证，先看现有实验为何未通过 | 不减采样、不改阴影遮挡集合/积累顺序、不启用近似解析阴影或新的反射策略 |

这些都是待验证假设。当前没有足够证据承诺它们的整帧提升比例。若 P1 的剩余开销很小，应跳过该候选，不能用大重构强行追求收益。

## 5. 执行批次与交付物

### S0 — 建立可复现的渲染侧基准

1. 从基线创建 `codex/render-code-optimization` 分支，先检查工作区增量；后续其他任务改动与本方案单独提交，不混入对照。
2. 保存物理/开球/预测源码及资源哈希、实际 build settings、Xcode/OS/设备信息、默认渲染 profile。
3. 复用已有渲染测试与诊断，补充默认关闭的局部计数/计时：回调次数、被测段耗时、材质写入次数、分配次数/字节。不为每球每帧写日志，不让计时探针自身制造大量对象。
4. 建立固定盘面与录制好的输入/播放序列；直接重放同一份运动数据，避免每次重新随机开球或重新求解污染渲染对照。真实击球流程另做集成回归。
5. 对基线重复采样，先知道自身波动和采样开销，再选择第一处可解释热点。

交付：配置清单、输入 fixture、原始数据、统计脚本与热点结论。只有测量支持的入口进入 S1。S0 的测试计数和合成回放不改变生产物理。

### S1 — 一处 CPU 热点的最小重写

优先选择 S0 确认成本明显且容易保持行为的入口。每次只改一个原因：消除重复读取、去除实际临时分配，或将固定布局移出循环，避免同时引入多套缓存。

缓存必须明确：保存什么、由谁访问、何时失效、何时释放。节点列表缓存绑定场景/球拓扑代次；数值快照绑定同一渲染回调。稳定顺序保留球身份和 shader 索引关系，不能把字典遍历的顺序变化传到阴影累乘中。

纯计算函数应使用具体输入/返回值、可控循环和局部变量，帮助编译器看清数据依赖；是否内联或拆函数依照 `-O` 后实际代码与性能决定，不按代码长短判断。

交付：一项小提交、前后调用/分配数据、数值一致性与动态图像检查。没有稳定收益则撤回实现，保留结论。

### S2 — 渲染提交与生命周期

只处理 S1 后仍存在的调用开销，检查是否有重复的相同值 SceneKit 写入、重复构造参数对象或无效材质访问。已有变化检测和合并提交保持原语义。

线程边界先验证：主线程 DisplayLink、SceneKit 渲染回调和 SCNAction 不可假定同线程。不能为了少一次锁而删除同步，也不能把同帧参数更新移到异步主线程或嵌套 transaction，造成球影晚一帧。Data 仍需保持 GPU 消费期间不可变。

交付：提交计数、同帧球影证明、快速重开/取消/离页恢复检查。若生产只有一个材质引用，不再重复做无收益的材质去重实验。

### S3 — 可选的 GPU 公式复用

前提：CPU 批次完成，而且当前真机数据仍支持 shader 是主要限制。先核对原公式、变量作用域、采样分支和既有失败案例，再选择一个相同输入的重复表达式进行改写。

保持样本数量/位置、球遮挡过滤、光源、材质参数、浮点精度、累积顺序与 shader 接口。代数上等价不代表有限精度下像素相同，必须实际对拍。现有 `factorClothBRDF`、`mergeClothSupport` 只能当研究入口，不能因为开关存在便视为已验收。

交付：原/新 shader 差异、参考数值/图像对拍、真机 GPU 数据。不成立则维持当前生产 shader，结束该批。

### S4 — 集成验收与默认值交付

复核所有被触及页面，完成固定画质真机配对比较。合格改动逐批保留；互相有依赖的最终组合还需测一次，不能把各批局部收益直接相加。完成后提供普通构建、安装包与实测报告，明确手机体验仍需用户确认的部分。

## 6. 测量方法

全部 A/B 使用相同 `-O`、设备、OS、渲染尺寸、请求帧率、profile、输入序列和探针配置；比较基线 A 与一项候选 B。模拟器主要证明行为和局部 CPU 趋势，真机决定最终 CPU/GPU 收益。

固定场景集：

| 场景 | 主要检查 |
|---|---|
| 2D / 3D 静止瞄准 | 停绘、唤醒、静止材质提交为零 |
| 15球固定开球轨迹回放 | 多球运动、球影同帧、动态 CPU 与 GPU |
| 单球运动与落袋/淡出 | presentation 位置/透明度、球退出后的 uniform 权重 |
| 3D相机拖动/缩放 | 每帧画面、相机持续更新及输入延迟 |
| 快速重开、2D/3D切换、离页恢复 | 旧代次缓存释放、新场景初始化和资源增长 |
| 带自适应标签的角度页 | geometryKey、球身份变化、标签避让和 viewport 更新 |

真机短性能比较采用成组 ABBA，至少 3 组完整配对，每段统一预热与固定 20 秒有效窗口；缺段、录制失败、明显系统状态变化的组完整作废重测。屏幕亮度固定，局域网连接；涉及持续温升时先确认未充电、起始状态一致，另立长窗口验收，不从短跑推算温度。

保存每组原始数据与样本数。报告 CPU 被测段中位数/P95、分配和 setter 次数、完整帧的迟帧/卡顿，以及能够证明归属的 GPU 时间。命令 buffer 起止时间只能说明命令执行，不能自动当呈现 FPS；GPU 活动区间不能写成功耗或摄氏度。

收益判定：被优化指标在多数配对组方向一致，汇总差异超过基线重复波动；区间仍跨越零则记为未证明收益。整体帧时间、P95、内存和启动不能出现超过基线波动的持续退化。局部调用减少而整帧不变，应如实标为局部改进，不宣称全 App 加速。

## 7. 正确性验收

- 每批复核保护区源码和资源哈希；不变的物理无需为了渲染优化重新修改或标定。集成输入仍要核对同一录制轨迹被消费，避免测试 fixture 误变。
- 保留独立预期值或旧实现对拍，覆盖可见、隐藏、移除、抬高、透明度、球数非4倍数与场景替换。不能只断言新实现自己的输出。
- 复用 `RenderQualityV62Tests` 的 packing、idle/wake、动态图影等实际测试入口，并在修改前核对当前测试的覆盖范围；按候选补最少必要测试。
- 同设备/OS、相同姿态和时间点执行 A→B→A 图像对拍。CPU 数据组织改写目标为 RGBA 零差；若 A 自身不稳定，先固定环境并解释噪声，不能临时放宽阈值让 B 通过。GPU 改写同样不得以肉眼近似替代像素检查。
- 动态画面检查动画应用后同帧 presentation 位置、阴影与透明度；静帧相同不足以证明运动正确。
- 小屏手机/标准手机/iPad至少覆盖触及的布局；shader 或参数 ABI 改动同时验证现有 iOS 17 与当前 iOS 26 测试环境。
- 完成正常 build、相关定向测试、`verify-gate`、`verify-doc-size`、`git diff --check`。新输出写入需登记真实路径和清理边界。

新增证据放在 `build/render-code-optimization-20261001/` 对应批次子目录，含原始日志、截图、统计与哈希；报告区分模拟器通过、真机测量、用户体验、发布四种状态。

## 8. 回退与停止条件

每批独立提交，记录精确起点和改动文件。实验开关默认关闭，仅用于配对比较；最终只保留有收益且验收通过的路径。不使用 reset/force push 覆盖他人工作；需要撤回已提交候选时用针对该批的 revert。

出现画面差异、阴影延迟、缓存错代次、静止继续渲染、资源持续增长、旧系统 shader 失败，立即停止该候选并恢复基线行为。两轮受控比较仍无稳定收益，或收益来自减精度/减画质，结束候选并记录。

如果剩余耗时主要来自 SceneKit 内部，应用层已无明显重复工作，结论应是当前约束下收益有限；不能暗中迁移渲染引擎或降低画质。每批难度和工时根据 S0 的热点及验证规模再估算，不预先承诺倍数提升。

## 9. 开始实施时的第一项

执行 S0：固定基线和回放输入，在已有 `-O` 下测 `renderUpdate`、`MobileContactOcclusion.update` 与标签 geometryKey 准备的实际成本。选择证据最明确的一处做 S1 小改动，再决定是否值得继续 CPU 或 GPU 批次。基线与方案已先提交推送。S0 在独立分支加入默认关闭的 DEBUG 计时与回放诊断，未改变渲染算法；下一步由真机数据补充分配与整帧归属，只有证据明确的热点进入 S1。
