# 每日清台 2D 正常击球分段诊断

日期：2026-09-21。结论：本轮样本不支持“物理引擎在球运动期间持续重算”这一解释。持续负载主要落在 SceneKit 渲染链路；未优化 Debug 还明显放大预测和主线程轨迹构建成本。尚不能据此宣称已查明手机发热的唯一根因。

## 当前真实调用链

- 默认 `EventDrivenEngine.SimulationModel.appDefault = .planarReference`。历史空间袋口慢路径不是当前默认，不能套用旧性能结论。
- 普通进袋预测经 `PositionPlayShotSolver.solve → predictForPositionSolve`，使用解析瞄准评分及完整终验。自由瞄准经 `simulateFree`。本轮普通预测测试没有调用翻袋备选。
- `PositionPlayViewModel.play` 复用 `solvedShot.prediction.recorder`；`launchBalls` 通过 `TrajectoryPlayback` 和 SCNActions 播放。正常运动期间没有逐帧调用整套物理求解。
- 杆末 `finishStrike` 会为下一杆重新预测一次，因此计数窗口若覆盖收尾，可能多出一次求解，不能误判成运动期间重复求解。
- 2D 仍由 SceneKit 绘制球桌和球体；视角改为俯视没有移除这些渲染成本。

## 测试方法与范围

环境：同一 Mac / iPhone 17 Pro 模拟器（UDID 133B2301-328F-4952-8020-8140761544FB），iOS 26.3。当前工作区包含上一轮取消计算和高温帧率策略；本轮只新增诊断测试，不修改产品行为。

1. 固定中八 seed 52、真实开球后的15球盘面，生产 VM + SCNView + 生产 Coordinator，2D；分别1.5/3.6 m/s、每种2杆。各杆包含静止、重新预测、运杆/球运动、停稳后。`getrusage` 进程 user+system CPU 增量除以墙钟时间，100%表示占用一个CPU核；帧数取实际 didRender 回调。此宿主不含完整 FreePlay SwiftUI 工具层。
2. 同一上述四杆对照：优化 Debug `-O` / 60 FPS、优化 Debug `-O` / 30 FPS、未优化 Debug `-Onone` / 60 FPS。每次测试恢复原帧率偏好。
3. 普通进袋物理：seed 52–54，1.5/3.6 m/s，各6个袋口，36次尝试。其中12次几何可行、全部停稳；另外24次几何拒绝，不混入有效预测的耗时统计。没有翻袋调用。
4. 真实每日清台页面：自动开球 → 保持2D → 自由瞄准 → 刻度轮往返 → 正常击球 → 1杆0犯规、剩14球。独立 XCUITest 一次，按阶段外部 `ps` 累积 CPU time 差值统计，另采2秒调用栈。该样本不等于用户手机上原球形的逐杆重现。

## 结果

### 生产场景宿主，4杆中位数

| 指标 | 优化60 FPS | 优化30 FPS | 未优化60 FPS |
|---|---:|---:|---:|
| 击球前静止CPU | 2.50% | 2.50% | 3.18% |
| 播放阶段CPU | 15.83% | 9.35% | 16.95% |
| 播放实际帧率 | 59.94 | 30.02 | 60.03 |
| 停稳后静止CPU | 2.55% | 2.72% | 3.18% |
| 静止实际重绘 | 0帧/3秒 | 0帧/3秒 | 0帧/3秒 |
| 自由瞄准物理预测 | 11.94 ms | 13.26 ms | 49.32 ms |

每杆播放约5.8–6.4秒。仅降低渲染频率，播放CPU中位下降约40.9%，物理与轨迹复用路径相同；不是手机GPU功耗下降40.9%的证明。60 FPS优化组trial 1同时做外部sample，可能引入扰动，保留原始数据。四杆样本较少，不作统计显著性结论。

### 普通进袋预测（12个有效样本）

| 构建 | 中位耗时 | 最大耗时 |
|---|---:|---:|
| Debug + `-O` | 10.31 ms | 21.51 ms |
| Debug + `-Onone` | 53.83 ms | 119.38 ms |

未优化中位约5.2倍。36次尝试的可行性、进袋、停稳布尔结果完全一致；模拟时长最大差0.000095秒。这里并未验证所有轨迹点逐位相同，也不把优化Debug叫作Release。

### 主线程轨迹构建

生产 `entryTiming.trajectoryMs` 计量 `drawTrajectory`（包含清理/创建轨迹节点，不是GPU整帧时间）。固定自由瞄准四杆中位：

- 优化Debug：0.82 ms；对应整段 `apply` 0.95 ms。
- 未优化Debug：41.84 ms；对应整段 `apply` 41.97 ms。

这是本轮发现的、与普通瞄准相关的明确开销：未优化包在主线程生成轨迹时可占约2–3个60Hz帧预算。它和物理计算应分别处理，不能合称“物理引擎慢”。尚未对 `drawTrajectory` 内部细项做成本拆分。

### 完整页面（优化Debug，单次正常击球）

| 阶段 | 观测区间 | 平均CPU |
|---|---:|---:|
| 击球前静止 | 5.46秒 | 1.65% |
| 刻度轮调整瞄准 | 2.07秒 | 32.86% |
| 击球前重新静止 | 3.12秒 | 2.25% |
| 点击/运杆/球运动至杆末 | 5.96秒 | 24.50% |
| 停稳后 | 5.98秒 | 3.01% |

完整页面与独立宿主的球形、视口、UI/AX负载不同，不能直接相减算出SwiftUI成本。sample会造成采样扰动，ps累计时间仅有0.01秒精度。

播放采样片段出现 `SCNRenderer → C3D::RenderGraph::execute → DrawNodesPass`，独立宿主也有少量 `TrajectoryPlayback.stateAt`；两份播放片段均未见 `ShotPredictor/EventDrivenEngine`。瞄准片段则能看到 `simulateFree/EventDrivenEngine`。sample包含等待线程，不能将其调用次数直接折算成CPU或GPU利用率；短片段没有采到某函数也不证明整次运行从未执行。

## 判断及下一步

**已支持的判断**：普通击球的物理计算是短时预测；2D在运动期间仍付出持续的SceneKit渲染成本；未优化Debug显著放大物理预测和主线程轨迹构建。静止后负载回落，没有复现不停求解或不停重绘。

**尚不能确定**：手机安装包的准确编译优化设置；手机真实GPU带宽/着色器瓶颈及功耗；1.73 GiB峰值内存资源归因；其他复杂球形、高低杆及长时间连续击球是否存在不同热点。模拟器使用Mac CPU/GPU，不能单靠这些结果排除手机上的物理热点，也不能据此保证降温。

建议优先用明确的优化构建做手机冷启动/冷却后对照；若仍热，按正常2D击球场景分离帧率、台呢接触阴影/球面材质及分辨率成本，记录实际GPU工作与热状态。只有测出单项差异再调整画质。物理层优先检查最慢真实球形及预测调用次数，不改碰撞规则或缩减求解精度。
