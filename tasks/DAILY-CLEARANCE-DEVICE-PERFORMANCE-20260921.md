# 每日清台真机性能采集（2026-09-21）

状态：本轮真机采集及离线分析结束；发热已复现，根因和公平2D/3D长时对照未闭合。用户授权连接手机后测试；直接附加现有球迹进程，未重装、未清数据、未修改产品。

## 环境与边界

iPhone 16 Pro / A18 Pro，iOS27.0(24A437)，有线连接、开发者模式开启；Xcode26.2/Instruments26.0(17C52)。安装版本为开发者App 1.0.0(1)，具体源码提交及优化级别不能由版本号确定，因此不是Release验收。当前仓库代码只能作为定位参考，不能默认等于安装二进制。

同一进程的自然操作与静止采样，非固定盘面/杆数的公平A/B。环境温度、亮度、充电状态和帧率偏好未控制；有线供电与采集开销可能影响热与功耗。

用户确认3D打开，然后确认2D打开。早期3D操作提示未得到动作完成确认，不标为有效击球压力场景。

## 采集工具异常与处理

- Game Performance模板默认Windowed(5 seconds)，最初60/90秒录制只导出10秒数据；原始结果保留，但不按完整采集时长解读。后续显式window90/120秒，并加入Activity Monitor，实际样本时间复核。
- xctrace导出有多次SIGSEGV/退出139。保存失败日志和重试文件；仅使用XML完整、可解析、字段/时间/进程可核对的数据。完整XML不意味着整个命令退出正常，二者分开记录。
- 一次window-check能力探测误与3d-active重叠，因kperf锁冲突失败，不计入性能通过；后续录制串行。该能力探测同时报告所选GPU counter profile不支持当前设备，不能报告硬件利用率/带宽计数器通过。
- GPU trace包含backboardd等系统进程以及无归属区间，必须按球迹PID归属过滤，不能将系统合成器消耗算作球迹。

原始证据：build/daily-performance-device-20260921/。隐私相关设备唯一标识仅留本地工具证据，不写进结论。


## 本轮实测结果

用户随后明确反馈「3D准备好了，而且已经明显烫手了」。此时2D操作采样的系统热状态为Serious，立即停止继续加压，取消计划中的3D操作复测；仅追加40秒Activity Monitor/Thermal State停止操作观察，之后全部手机端采集结束并告知可断开冷却。未进行安装、清数据、改设置或产品代码修改。

CPU百分比按进程累计CPU时间增量/采样墙钟时间计算，以单核100%为单位；峰值为约一秒Activity Monitor样本，非瞬时指令峰值。内存为physical footprint，不是GPU显存，也不是单纯RSS。

| 场景与有效口径 | CPU均值 / 单样本峰值 | physical footprint | 热状态 |
|---|---:|---:|---|
| 3D页面，44.50秒，操作未确认且未捕获球迹GPU执行 | 2.73% / 3.96% | 1590.7→1598.2MiB | Fair |
| 2D确认静止，44.36秒 | 2.89% / 4.07% | 1598.0→1605.3MiB | Fair |
| 2D操作指引窗口，74.05秒，已有CPU/GPU/显示活动证据 | 25.09% / 161.46% | 峰值1767.8MiB（1.73GiB），末尾1603.0MiB | Serious |

2D操作窗口采样均值24.88%，CPU累计时间口径25.09%，最终采用后者，先前口头约25%成立。约17.645秒处161.46%，42.215秒处84.0%；多数操作样本约14–50%，后段回落至约3%。动作次数与每杆起止未单独记录，不能保证与其他模式同等工作量。用户未单独确认“完成”，但CPU、Metal与显示事件证明该窗口不是全程静止。

Serious在2D操作trace的起始已存在，不能断言“这75秒2D操作导致由Fair升为Serious”，更不能断言2D比3D更热。早期能力样本为Nominal，后续为Fair，再到Serious；不同采集间有空档，非连续温升曲线。热状态不是摄氏度，也没有实测GPU频率证据来量化降频幅度。

## 真机GPU：有效发现与缺失指标

命令行若干GPU导出失败后，改用Instruments打开原始trace，展开GPU Channel Activity Summary → A18 Pro → 各通道 → 球迹(6138)，明确排除backboardd系统合成器。UI原文摘录在 `instruments-ui-observations.md`，可在原trace复查。

| 球迹GPU通道 | 可用片段累计执行时间 | 平均CPU→GPU开始延迟 | 单区间最长 |
|---|---:|---:|---:|
| Fragment（片元） | 1.92s | 7.82ms | 16.00ms |
| Vertex（顶点） | 584.47ms | 2.81ms | 11.77ms |
| Compute（计算） | 2.06ms | 1.99ms | 0.102ms |

这些是GPU通道区间，不是每帧完整耗时、GPU利用率或瓦数；通道可能重叠，不能把表内累计时间直接相加当总帧时长。最长片元区间已接近60帧预算16.67ms，但单个最大值不能证明长期GPU饱和。片元累计开销更高，是后续材质/阴影/屏幕像素成本对照的定位方向，尚未具体归因到某个shader。

**采样保留范围有额外限制**：即使显式扩大window，Activity Monitor覆盖完整约75秒，CPU调用栈/Metal/Display详细事件在原始UI中主要保留约57秒之后。Displayed Surfaces XML中事件起点范围57.227–64.728秒。GPU累计值和1255个CPU样本只对应保留片段，不能除以全程75秒算GPU利用率，也不能用此处调用栈解释17.6秒的CPU峰值。

能力样本的Metal current allocated size为630.52MiB，来源existing-capability.trace；这是当时的Metal已分配量，不等于纹理实际驻留量，更不能加到footprint上计算总内存。后续无分配记录的空表不代表0显存。

无法完成：GPU硬件利用率/带宽/tile/shader占用、可靠整段GPU帧分位数、实际功率/耗电速度。工具明确有counter profile不支持提示，未虚构这些指标。

## CPU与静止回调线索

3D完整窗口可解析的调用栈中，AngleSceneView.Coordinator.renderUpdate及updateFramePacing有采样；当前源码也确实在空闲时以最多30Hz运行CADisplayLink，遍历scene节点检查动画并更新标签。**停止SceneKit绘制不等于完全停止CPU回调。** 这可以解释“空闲GPU少，但CPU仍有约3%”的一部分，是可优化候选；具体贡献还需相同二进制的对照，当前安装包提交未确认。

2D保留片段1255个CPU样本，主路径包括SwiftUI显示链接、ViewGraph更新及AttributeGraph；没有足够证据把161%峰值归到翻袋求解器。之前模拟器求解成本仍是独立证据，不能冒充本次真机根因。

## 停止操作后的检查

cooldown-system.trace录制40秒并成功保存，可在Instruments打开。XML导出持续崩溃，UI某快照球迹仍约1.65GiB，但CPU百分比为空；不据此声称退出后CPU已降至某数值、内存泄漏或温度已恢复。没有用户回到主屏的确认/屏幕证据，因此这段仅称“停止操作观察”，不是完整后台验收。

导出崩溃是Mac端xctrace，.ips显示EXC_BAD_ACCESS/objc_retain及XRRemoteDevice.cachedBaseSymbolsPath路径；不应写成手机App崩溃。Xcode26.2与iOS27.0组合的兼容性需复核，现有证据尚不能证明版本差异就是崩溃根因。

## 优先级与下一步

1. **先查内存归属**：1.6–1.7GiB的进程footprint在本机现有包上确实存在，切2D没有大幅释放；拆分场景副本、原型缓存、纹理、压缩页与SwiftUI/模型保留。冷启动基线与Memory Graph/Allocations对照后，才判断缓存过大还是泄漏。切后台本身不要求清空全部缓存。
2. **做真机GPU单变量对照**：同一盘面、同一镜头/操作量，从正常热状态开始，逐项比较帧率、渲染比例、阴影/反射和纹理规格；优先看片元成本。不能照搬模拟器“GPU很轻”的结论，也不先全面降画质。
3. **减少不必要CPU工作**：核对空闲CADisplayLink遍历与标签更新的必要性；再对连续瞄准、换袋求解做调用计数及过期计算取消/缓存实验。未实施任何优化。
4. **补公平2D/3D对照**：这次因Serious及明显烫手停止，3D主动操作对照与长时热稳定性仍未完成。后续待自然冷却、确认发布优化级别，优先低干扰分项采集，避免一次开启大量追踪引入热开销；环境、亮度、供电和帧率保持一致，并交叉模式顺序。

本轮结论是“实际手机上复现严重热压力，并取得GPU/CPU/内存负载证据”；不是“已锁定单一根因”，也不是性能修复或发布验收通过。
