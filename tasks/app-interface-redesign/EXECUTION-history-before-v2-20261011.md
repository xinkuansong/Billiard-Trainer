## 2. 每页的现行版本核验

设计前必须区分四份事实：

| 对象 | 必记字段 | 如何核实 |
|---|---|---|
| 当前源码 | 分支/HEAD、相关 dirty/untracked、文件 hash、符号、核对时间 | 读当前工作区及真实调用链，不能只看旧文档/HEAD |
| 最近设计 | Figma file/node、版本/日期、用户选择、本地/云端状态 | 读取实际稿及最近有效决定；未找到就写未找到 |
| 原生画面 | 构建来源、设备/Runtime、数据/权限、截图/录屏 | 从真实生产入口进入；测试深链只作补充 |
| 最近验收 | 哪个版本、哪些状态/设备、用户原意、尚未验什么 | 链接具体记录，不能把“旧批完成”移植到新版本 |

先填页面版本记录；代码/设计/实际画面对不齐时写明差异和采用依据。未核验的页面状态为“现行视觉待核”，不得用于 Figma 重设计基线。历史文档保留但标注用途为历史参考；新日期文件也不能直接取代明确获准版本。

**设置示例**：当前全局设置位于 `Profile/Views/SettingsView.swift`；每日菜单在 `PositionPlay/Views/DailyHUDPanel.swift` 等。两者不是同一页面。“设置声音”为全局设置内联分区，并不是已经核实的独立声音页。旧 PROGRESS 的 T-P8-05“球种+周目标”仅记录早期交付，不能作为当前设置页全量内容。

## 5. 集成与独立验收

1. 执行者自证：白名单 diff、逐条 DoD、完整日志/xcresult、前后原图、生成条件及所有未完成项。只汇报“测试通过”不足以交付。
2. 主控/astra 逐文件审查并亲自打开原始证据；核对成功/失败/跳过数、覆盖项、截图内容、源码版本及有没有删改断言来放行。只读规划核对源码，不冒充正式 Phase QA。
3. 代码分批串行集成；每合一批，在整合树构建及运行该批适用检查后才合下一批。文档批不要求 iOS build。
4. 既有测试可复用，但必须确认对象未变化、证据可归属；合并冲突、跨批共享变化或证据存疑时补跑受影响的最小测试面。不能用旧截图验证新代码。
5. 业务代码冲突退回原执行者基于新基线修订，主控不随意拼接。失败保留原日志和 F-ID/适用 FL，返工用原批 ID 加 `r2/r3`，不把失败轮次覆盖掉。
6. 工程验证、模拟器视觉、用户确认、真机手感、安装、提交、发布分别登记。只有全部本批 DoD 满足才记 ✅；依赖用户体验的最终收口保持未完成。

## 6. 每次生成与每批结束的回写顺序

**生成时**：文件实际保存 → 写原始 manifest → 在 ARTIFACTS 增加 A-ID（可按组登记但 manifest 必须列全文件）→ 批次卡链接对应 DoD。包括研究、粗稿、精稿、弃用稿、失败截图、日志、源文件、备份和临时评审图；临时文件若不构成交付可归一组，注明用途和保留状态。

**批末/中断时**：

1. 批次卡写已过/未过 DoD、真实结果、返工和原始产物。
2. DECISIONS 记录用户选择与反馈；新需求更改 PLAN 版本、依赖和受影响批。
3. PAGE-INVENTORY 更新该页面当前阶段、已覆盖状态、采用的 A-ID 以及未覆盖项。
4. ARTIFACTS 更新适用/被替代关系、验证层级和保存位置；不删除旧候选。
5. CURRENT 更新唯一批次状态表、当前成果、阻塞与**一个明确下一动作**；带上活动 worktree/资源占用。
6. PROGRESS 与 Hub 写简短摘要和 CURRENT 链接；遵守近 10 条与体积门禁，必要时归档旧记录，绝不抬阈值。

不把同一份完整状态表复制到 PLAN/Hub。发生不一致时核对一手证据后修复 CURRENT，而不是猜哪个“最新”文件可信。
