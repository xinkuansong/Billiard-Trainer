# 全 App 原生截图与 Figma 评审实施方案

**版本 v4.0｜2026-10-11｜本文件是本轮需求真源。** 承接用户对Figma评审图册、修后截图替换和并行提速的确认，覆盖v3.0的本地网页优先及全程串行安排。用户已追加授权执行；采集与 Figma 建册已启动，实际状态见 CURRENT，App 修复另计。原可编辑设计系统全量复建继续暂停。

## 1. 目标与已确认要求

利用已经可运行的 App 建立可浏览、可追溯的全量截图基线，集中发现问题，再按已确认的修改方案修复代码并重拍验收。实际运行界面是现状依据；**Figma是用户主要评审入口，本地原图与manifest是证据真源，APP-ISSUES是问题状态真源。** Figma中的截图保持为图片，只在需要讨论新设计时另做可编辑候选；长期设计系统随实际改进积累。

用户已确认：

1. 覆盖整个 App 的页面和重要状态，而不只是五个首页。
2. 先覆盖既定五个窗口档位和浅深模式；其他设备/Runtime 后续扩展。
3. 所有截图来自真实 App，直接保留真实图标、字体、材质、图片与交互状态。
4. AI 先检查错页、漏图及明显问题，再由用户集中审阅；不让用户承担基础找错工作。
5. 现有不合理之处记入问题台账，区分确定缺陷、待验证疑点和需要选择的设计改进。
6. 复用已有截图和测试，但必须核对版本、状态与范围；不全部从头制作。
7. 允许资源隔离的有限并行：默认两路独占设备采集，离线检查可与采集重叠；共享基线、中央台账和Figma写入由主控统一管理。同一设备、桌面焦点和Figma文件不多写。
8. 保留已有Figma、原生证据和验收记录，不把旧Figma完成数转换成新截图完成率。
9. Figma按业务域Page、页面Section、状态组和尺寸/主题截图槽位组织；更新保留修前图与评论依据，新版重新评审。

主流程：**固定App版本 → 页面/状态清单 → 并行原生采图与AI初审 → 串行导入Figma → 用户评审 → 确认修改 → 代码修复 → 受影响状态重拍 → 更新Figma并复审。**

明确缺陷可在后续获准执行的修复批中直接处理；新的布局、视觉风格或业务口径变化先给具体候选。当前“重新写方案”不自动启动采集、Figma写入或App改码；下一次要求继续时从本方案N00执行，不恢复旧复建队列。

## 4. 截图方法与数据一致性

### 4.1 固定输入

每轮登记App提交/实际源码差异、构建配置、bundle版本与产物哈希、资源版本、Runtime/UDID、逻辑窗口/像素比例、语言zh-Hans、时区Asia/Shanghai、字号、系统主题与App有效主题、fixture ID与内容摘要。

同一比较组使用固定的测试身份、记录/模版UUID、标题、封面、剂量、计划状态、日期与完成数据。可用现有内存容器或独立测试seed；持久化流程另测。跨重启必须重新建立相同fixture。状态栏时间可统一，但不得靠后期修图隐藏业务日期、计时、字体或图标差异。动态字段记录差异；动画稳定帧与计时冻结仅允许显式测试控制，标注其范围。

优先正常导航进入；测试深链/夹具只用于明确的状态准备，标注“测试入口”，并另有正常入口验证。当前旧巡游的“存在才点”不能作为缺页成功：每个预期条目必须产出有效图或明确失败/阻塞。

### 4.2 单次采集

1. 核对本批范围与版本，使用本任务独占模拟器；记录初始状态，只有本轮取得的资源才有收尾权限。
2. 启动指定构建和fixture，核对页面身份、关键业务文字、有效主题与实际窗口。
3. 通过现有UI测试或获准的原生UI工具操作；不以运行时强改视图属性制造通过。
4. 等布局和资源稳定后保存原始PNG、必要的AX/日志及manifest。纯截图通常不需要逐节点LLDB几何取证；只有截图/交互无法解释的局部问题才升级诊断。
5. 长页先拍顶部，再分段滚动覆盖实际内容和底部；相邻图保留上下文，核末尾标志或真实滚动结果。普通截图拼接只作阅读辅助，不作为真实可见窗口/无遮挡证据。
6. 核对漏图、重复错页、尺寸、可解码性、异常空白及主题；逐张正常显示尺寸看原图，缩略联系表仅用于定位。
7. 及时更新图册和进度，收回本轮启动的App/模拟器资源，保存失败原件。

### 4.3 失败时停止扩大成本

同一路径第一次失败先判定是导航、fixture、构建、环境还是App问题；最多一次有证据支撑的修正重试。仍失败就保存命令/原图/实际状态和下一可行办法，将该项标BLOCKED并继续独立页面。若整个采集链失效，只暂停依赖它的批次。

工具开发预算以交付为约束：N01只做一个可用的采图到评审闭环；不先重写整个自动化框架。重复字体探针、重建Figma图标、云库传播、全节点几何导出均不属于当前采图前置。采图中发现App缺陷先记录并保留截图；只有阻止后续采集的缺陷才单独提最小解阻方案。

### 5.2 页面内部布局

每个实际页面一个Section，头部放入口、baseline、fixture、覆盖/评审状态、问题编号。每个业务状态一个组：手机小/标准/大为三列，浅/深为两行；iPad竖/横另排两列浅深两行。长页每一槽位按顶部→中段→底部排列，保留切片顺序和真实窗口边界。弹窗、菜单、键盘用独立状态组，保留宿主背景。

图片按`像素尺寸/真实scale`放置，保持原比例并使用对应逻辑窗口大小；不统一拉伸成同一宽度。文字标签放在截图外，不盖住App内容。首次导入检查小字、细图标、长图切片和Light/Dark对应关系；不依赖缩略图判定清晰度。Figma导入若改变分辨率，保留本地原图链接并实看可读性，未通过的不能标已交付。

### 5.3 稳定槽位和批量更新

逻辑`slotId`由页面、状态、内容/入口变体、设备档位、方向、主题、滚动段组成，**不含版本号**。每次实际采集生成独立`captureId`，绑定baseline、fixture、原图SHA和尝试号。`figma-map.json`记录slotId→fileKey/pageNode/sectionNode/frameNode/imageNode及currentCaptureId；节点名称帮助人找图，机器定位以真实ID和slotId映射为准。

导入者只接收完成原图检查的队列：同slot同hash重复提交直接跳过；新hash进入更新流程；无明确slot或来源错配则拒绝。每次按一个页面状态组小批写入，保存回执并读回节点/图片/尺寸。未知结果先读回，不整页重导。不为几十张图片生成庞大的可编辑图层树。

修后更新：保留旧截图及其captureId/评论依据→核新图同状态→更新当前槽位→标“待复审”→建立前后对照→用户复审→归档旧版。**稳定的是Section与逻辑槽位，不保证替换或移动节点后平台评论仍保持正确锚定。** N01必须实测一种保留评论语义的更新办法；若直接替图无法保证，保留原评论节点及旧图，新增修后图并更新当前映射/入口。不能用复制画板代替评论备份，也不能替图后把旧评论当新图反馈。

只重拍和更新受影响范围；公共组件改动先列所有消费者，跨页面/尺寸复验。未受影响旧图继续显示真实版本/复用依据，不为了“最新”更改标签。

### 5.4 本地文件与评论回收

```text
output/app-native-audit/<baseline>/
  manifest.json                 # 由各采集批次汇总的证据目录
  capture/<worker>/<batch>/<attempt>/  # 原始PNG、日志、分批清单
  review/                       # AI核查、用户意见快照、前后对照
  figma/import-queue/           # 已审待导入小包
  figma/figma-map.json           # 真实节点与当前截图映射
  figma/receipts/                # 每次导入/替换的读回回执
  backup/                       # 文件清单、.fig及恢复检查结果
```

沿用v3的capture字段，增加slotId、导入状态和Figma节点链接。Figma保存圈图/评论供用户评审，本地APP-ISSUES维护问题处理状态；评论同步记录评论链接/ID（可取得时）、作者、时间、原文、captureId、图像hash和处理决定。N01核当前工具能否读评论；若接口不可用，通过正常UI逐条记录并保留证据，不假装实时双向同步。

用户不需要同时维护Figma和JSON。主控在每轮开始及评审后回收新增/变更意见，对应到问题编号；未取得的评论标待同步。评论“已解决”不自动等于App已修，问题关闭仍需修复版本/复验依据。AI可以标“已修待复审”，不能代替用户给“已认可”。

本地网页降为已有工具可顺便生成的离线备用入口，不再新开发第二套评论/评审系统。Git保存方案、必要工具及小型映射/反馈记录；原图按output规则本地保存。Figma云端保存、可下载.fig、原图+manifest备份分别验证；下载成功不等于独立恢复成功。跨版本图册应能按清单重建，评论证据单独保存，不假定.fig包含完整评论历史。

## 6. 双状态验收与问题修复

截图采集状态：`PLANNED → CAPTURED → VALIDATED`；缺环境/入口为`BLOCKED`，失效为`STALE`，N/A附依据。

Figma交付状态：`NOT_IMPORTED → IMPORTED → VERIFIED`；只能以实际写入回执/读回和目视核对计VERIFIED。

视觉评审状态：`UNREVIEWED → AI_REVIEWED → USER_REVIEWED`。意见分“可接受”“需修改”“待讨论”，记录真实评审人。AI审查与用户认可分别计数。

**真实呈现App缺陷的截图可以是VALIDATED，页面本身仍有OPEN问题。** 不要求修完所有问题才能完成截图基线；截图无错页/漏图不等于设计或交互通过。

继续使用[APP-ISSUES](APP-ISSUES.md)，不复制第二份缺陷正文。每条含发现版本与截图、现象/影响、确定性、严重度、期望依据、源码位置、受影响页面/尺寸、用户决定、修复提交和复验图。旧APP-I001遮挡、I003裁切、I006完成口径、I007重复标识分别复核，不把自动化风险推断成用户可见故障。

修复按共享根因归组：先明确期望和根因，再选共享组件/单页最小修改，运行必要构建与定向测试，原失败设备复拍，受影响其余档位/双模式及共享消费者回归。交互问题还要操作验证；统计、数据删除、存储等问题不能靠截图结案。

局部确定性修复在获准批次中直接落实。布局重构、配色风格或业务口径取舍提供原图标注/简短候选，必要时Figma出方案，用户选定后改码。沿用已批准规则不逐页重复请求；新取舍不得替用户决定。

修复后建立新基线：保留旧图，以源码/资源依赖查受影响页面，重拍受影响矩阵，再补五首页和核心链路冒烟。未变化的图如复用必须标原版本和复用依据，不把新旧图都写成新构建原生实采。

### 7.2 并发资源合同

- **默认2路采集，当前阶段不扩至3路。** 启动前检查空闲内存、磁盘、现有设备和别的任务占用；不强关非本任务模拟器。不承诺两倍速度。两路实测比单路更慢或出现资源型AX/进程故障，就降为1路，保留失败。
- 每路独占UDID、App沙盒/fixture、DerivedData、xcresult、输出目录、测试参数和临时工程容器；不得共享`/tmp/shot_dir`文件或让两个任务分别控制同设备浅/深模式。若同一Pad承担横竖，方向也串行。
- 先冻结源码并构建/预热，再使用经验证的构建产物。不能同时重新生成或写同一`.xcodeproj`/构建目录。已有runner使用`test`且同配置project可能共享，N01须验证独立临时容器或可靠的预构建执行路径；不因已有`--workers`就称环境已经隔离。
- **桌面UI自动化同一时刻只有一个操作者。** 独立UDID的XCUITest采集可在试跑证明确实不互抢焦点后并行；依赖CUA前台窗口的人工式导航必须排队。可在一台采集时离线审另一批，但不能两个agent同时点Simulator或Figma。
- Figma只有一个写入者。离线生成图片导入包可并行；写文件、页面、节点和current映射串行。与采集共用前台时也串行；前台独占不得靠不同Page名称规避。
- 已完成的小批以不可变manifest交接；采集者不编辑中央CURRENT/APP-ISSUES。主控按稳定slot去重、汇总；两个批次认领同slot就阻断后者，不采用最后写入覆盖。
- 通常保持最多2个小批“已审待导入”；若Figma/审查跟不上，先消化队列再扩采，避免成堆未核原图。不以未导入截图计Figma交付。
- 并行工作单元不必各启动一个智能体。优先单主控管理两个已验证的采集进程；需要子智能体时仅承担明确只读盘点/原图审查/独立输出，按项目模型选择规则在实际派发前确认和登记，不能沿用不可用的Cursor模型名。当前方案编写未启动子智能体。
- 每路只释放自己本轮取得的资源；一条失败不终止另一条安全的独立任务。新增工具改动串行验收后才冻结给所有worker，避免边采边换代码。

每批只保留一张任务卡：范围、依赖、输入版本、预期槽、worker/资源归属、结果计数、问题ID、证据链接、阻塞、下一动作。一次只分1–3个相关页面族，不为并行增加重复报表。
