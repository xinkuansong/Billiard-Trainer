# 按重组方案推进批次执行

输入是一份「本文件是本轮需求真源」的方案文件（含批次表、依赖图、完成标准、锚点索引——即 `issue-collection-restructure` 的输出契约）。本技能定义**怎么正确消费它**：不改方案语义、锚点重核实、验收用真实输出、批间状态清晰。

## 核心流程

1. **锁定真源**：找到声明为真源的方案文件，确认最新版本（高版本覆盖低版本）、状态、排期前置。前置条件未满足时先报告，不开工。
2. **选批次并核对依赖**：对照方案依赖图 + 项目进度台账（如 `tasks/PROGRESS.md`）确定本次做哪个批次。前置批次是否真完成，**以代码/测试实证为准，不信文档自述**。
3. **批前回显**（动手前输出）：
   - 本批范围 + **明确不做的事**（相邻批次的内容点名排除，防范围蔓延）；
   - **锚点重核实**：方案里的文件/行号是写方案当天的快照，动手前必须重读代码确认，漂移了先修正认知再动手，禁止按过期行号盲改；
   - 本批命中的红线/约束条目（回归面、几何契约、ADR 触发等）。
4. **执行中的冲突处理**：发现方案与代码现实冲突（锚点消失、假设不成立、目标达不到）时，**不擅自改方案语义**——小偏差在交付说明中如实记录；大偏差停下报告，等用户裁决；拍板后的变更**写回真源文件并升版本号**，禁止口头改方案。
5. **验收**：逐条对照该批次的完成标准，全部用真实输出（build / test / benchmark / 截图）证明，禁止凭估计或记忆宣称通过。做不完就如实说卡在哪。
6. **收尾回写**：真源文件批次状态（✅ + 日期）、项目进度台账检查点、命中项（如 ADR、FAILURE-LOG）、以及声明下一批是谁、依赖是否就绪。

## 批次节奏（默认一批，可连做）

- 以**一个批次**为基本推进单位：做完 → 验收 → 回写，形成完整闭环。
- 闭环完成后，同时满足以下条件可在同一会话连做下一批：下一批依赖已就绪、量级为 S/M、当前会话上下文仍充裕。
- 连做时**每批仍独立验收与回写**，禁止两批工作混在一起交付。
- 下一批是 L 量级、或本会话已累计大量编辑/命令步骤时，收尾并建议新会话继续。

## 红线

- **不改需求语义**：执行侧只落地，不增删、不弱化方案条目；变更必须经用户裁决并落回真源文件。
- **锚点过期重定位**：行号漂移时重读代码再动手，不盲改、不臆测。
- **不跳依赖**：前置批次未实证完成不得开工后续批次。
- **诚实验收**：宣称完成必附真实输出；宁可报「未验证」也不预支承诺。
- 正文用简体中文；代码标识符英文。
