# 复杂方案 → 贴合代码实际的可执行任务拆解

用户给一份复杂的问题清单 / 方案 / plan 时，**先摸清代码里的真实情况，再把它拆成能落地、能分会话干的任务**。重点是拆得符合实际，不是套某个固定格式。

## 核心步骤

1. **读懂原始诉求**：逐条理解用户要什么，去重、合并同类项，识别哪些是跨多处的通用要求、哪些是单点特有问题。
2. **对照真实代码**：动手拆之前先查代码——每条要求落在哪个文件/组件/函数、是共享层还是单页、改动波及面多大。锚点必须读代码确认，不确定就写「待定位」，禁止臆测组件名或假设结构。
3. **按依赖 + 可合并性拆批次**：
   - 能在共享层一次改掉、多处受益的，抽出来先做（做成后续复用的基准）。
   - 有前后依赖的排序；相对独立的可并行或换序。
   - 每个批次控制在**一次会话能完成并验收**的粒度。
4. **每个批次写清**：范围（做哪些条目）+ 依赖（等谁先做）+ 完成标准（怎么算做完，含构建/测试/截图等可验证项）。
5. **落成清单**：输出重组后的任务清单，通常存成新版本文件（如 `问题集合_v{N+1}.md`），并声明它是本轮需求真源。

## 输出契约（必备结构）

产出的方案文件是下游执行技能（`plan-batch-execution`）的输入，以下几节**必须齐备**：

- **真源声明**：文件头注明「本文件是本轮需求真源」+ 日期 + 状态 + 排期前置（若有）。
- **需求回显**：用户拍板结论逐条列出，作为语义基准。
- **批次表**：每批含范围、量级、依赖；附依赖图；每批附完成标准（含可验证项：构建/测试/截图等）。
- **锚点索引**：涉及的文件/组件/行号，全部读代码核实过，注明核实日期。
- **版本记录**：每次方案变更升版本号并记录变更原因，高版本覆盖低版本。

## 惯例与红线

- **不改需求语义**：只做重组织和拆解，不增删、不弱化用户诉求。
- **锚点要真**：组件/文件名先读代码核实；拿不准写「待定位」，别编。
- **几何/坐标类**：涉及角度、坐标、瞄准点的任务，动代码前遵循 `geometry-spatial-reasoning` 技能，禁止脑算断言。
- **贴合实际优先**：拆解要基于代码现状（改动成本、共享程度、依赖），别为了形式好看而硬凑批次。
- 正文用简体中文；代码标识符英文。
