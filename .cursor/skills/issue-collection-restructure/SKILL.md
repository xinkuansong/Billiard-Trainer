# 复杂方案 → 贴合代码实际的可执行任务拆解

用户给一份复杂的问题清单 / 方案 / plan 时，**先摸清代码里的真实情况，再把它拆成能落地、能分会话干的任务**。重点是拆得符合实际，不是套某个固定格式。

## 核心步骤

1. **读懂原始诉求**：逐条理解用户要什么，去重、合并同类项，识别哪些是跨多处的通用要求、哪些是单点特有问题。
2. **对照真实代码**：动手拆之前先查代码——每条要求落在哪个文件/组件/函数、是共享层还是单页、改动波及面多大。锚点必须读代码确认，不确定就写「待定位」，禁止臆测组件名或假设结构。
3. **按依赖 + 可合并性拆批次**：
   - 能在共享层一次改掉、多处受益的，抽出来先做（做成后续复用的基准）。
   - 有前后依赖的排序；相对独立的可并行或换序。
   - 每个批次控制在**一次会话能完成并验收**的粒度。
   - **合理设置会话（批次）数量——这是一个折中**：批次拆得多，每个会话上下文短、执行完整可靠，但每次会话都要重新读大量方案/代码，重复成本高；批次拆得少，单会话任务过重、上下文过长会触发压缩，导致细节遗忘或执行不准。原则：
     - 以「单批次工作量 + 需读的上下文」估算会话负载，上限是**执行到验收全程大概率不触发上下文压缩**。
     - 在不超上限的前提下**尽量合并**强相关条目（同文件/同组件/同一验收方式），减少需要重复读入方案和代码的会话数。
     - 数量本身没有标准答案，按实际负载判断；只在两端做检查：某批明显塞不进一次会话就拆，某几批读的上下文高度重合且总量不大就合。
4. **每个批次写清**：范围（做哪些条目）+ 依赖（等谁先做）+ 完成标准（怎么算做完，含构建/测试/截图等可验证项）。
5. **落成清单**：输出重组后的任务清单，通常存成新版本文件（如 `问题集合_v{N+1}.md`），并声明它是本轮需求真源。

## 输出契约（必备结构）

产出的方案文件是下游执行技能（`plan-batch-execution`）的输入，以下几节**必须齐备**：

- **真源声明**：文件头注明「本文件是本轮需求真源」+ 日期 + 状态 + 排期前置（若有）。
- **需求回显**：用户拍板结论逐条列出，作为语义基准。
- **批次表**：每批含范围、量级、依赖；附依赖图；每批附完成标准（含可验证项：构建/测试/截图等）。
- **锚点索引**：涉及的文件/组件/行号，全部读代码核实过，注明核实日期。
- **版本记录**：每次方案变更升版本号并记录变更原因，高版本覆盖低版本。

## 惯例与红线

- **不改需求语义**：只做重组织和拆解，不增删、不弱化用户诉求。
- **锚点要真**：组件/文件名先读代码核实；拿不准写「待定位」，别编。
- **几何/坐标类**：涉及角度、坐标、瞄准点的任务，动代码前遵循 `geometry-spatial-reasoning` 技能，禁止脑算断言。
- **贴合实际优先**：拆解要基于代码现状（改动成本、共享程度、依赖），别为了形式好看而硬凑批次。
- 正文用简体中文；代码标识符英文。

## 经验教训

### ⛔ FL-026 — 用户口语术语被单方面映射成通行方法，未回确认即写入真源
**场景**：用户诉求里的方法/概念名带「名字可能不准确」之类标注，调研阶段把它映射到某个网络通行方法（如「撞击点瞄准法」→重合比例法）后直接写入方案 §调研口径并据此派发，交付后被用户指出定义与原意不符，整批内容返工。
**强制检查点**：
1. 凡用户标注「名字可能不准确 / 大概叫」的术语，调研映射结果**必须列入拍板项**，格式「你说的 X = 通行的 Y（一句话定义）？」，用户确认前该定义只能标「推测」。
2. 含定义映射的批次，委派提示词中的方法定义必须逐条附「用户原话 → 采用定义」对照，让执行者也能发现映射断裂。

### ⛔ PD-027 — 方案审核两问：写盘测试盘点 + 断言前提验证（来自 v29 审核，2026-08-06）
**场景**：①批次完成标准写了「跑全量测试后工作区/某目录零 diff」；②批次范围含「修正/删除某条既有断言」。
**强制检查点**：
1. **写盘测试先盘点全集**：凡完成标准依赖「测试后零 diff」，方案里必须先列出**全部**会写盘的测试用例（`rg -l "\.write\(|FileManager.*create" <TestTarget>/` + 查 scheme/testplan 确认默认执行集），gate 范围以盘点结果为准，禁止只 gate 已知的那一处（v29 W1 原文漏了 `V21W2/3/4BakeTests`，按原范围执行验收必翻车）。
2. **改/删断言须附失败机理**：任何「修正/删除断言」子任务，方案里必须附断言原文 + 它在什么改动后、以何种机制失败的推演；裸构造的默认值断言通常不受新赋值路径影响（v29 原文误判 `XCTAssertNil(session.planId)`「必然失败」并计划删除，实为合法默认值测试——照做即「删断言求绿」）。FL-027 管实现期，本条把同一纪律前移到方案期。
